# fsMCP

MCP server providing file system tools via stdio. 10 tools, 1 category. TypeScript/Node.js. One runtime dependency (glob). No shell: nothing here reaches `execSync` or a shell string; `execFileSync` with an argv array is the only way this process ever spawns anything (ripgrep, for `fs_grep` and `fs_find`).

## Architecture

Single-threaded stdin/stdout MCP server. Newline-delimited JSON-RPC 2.0. Protocol version `2024-11-05`.

```
src/
  main.ts        Stdin loop, JSON-RPC dispatch (initialize, tools/list, tools/call), _meta narrowing (C1)
  types.ts       Wire types, MCPTool interface, result helpers (textResult, errorResult, scopeViolationResult)
  registry.ts    ToolRegistry class + JSON schema builder helpers
  security.ts    Path validation against allowed_dirs (_meta + CLI flags), _meta narrowing rule
  vpath.ts       Virtual <-> host path translation (issue #7), layered on top of security.ts, never inside it
  tools/         One file per tool, each exports register(registry)
```

Entry point reads stdin line-by-line, dispatches to `ToolRegistry`, writes JSON to stdout. Synchronous.

## Tools

All ten tools are category "File System" -- there is no second category any more (the old "Shell" category, and `fs_bash` with it, is gone: see "fs_bash removal" below).

| Tool | Read-only | Backend |
|------|-----------|---------|
| fs_read | yes | fs.readFileSync (raw bytes), strict UTF-8 decode, cat -n format |
| fs_glob | yes | glob npm package, relative patterns only, mtime sort, 1000-result cap, wall-clock budget |
| fs_grep | yes | ripgrep (rg) with Node.js fallback, wall-clock budget |
| fs_list | yes | fs.readdirSync, one directory, non-recursive, 5000-entry cap |
| fs_find | yes | `rg --files --no-follow` (Node walker fallback) + in-process fuzzy scoring, 200-result cap |
| fs_write | no | fs.writeFileSync (text or base64 bytes), auto-creates dirs, refuses a grant root as target |
| fs_edit | no | split/join literal string replacement, UTF-8 text only, refuses a grant root as target |
| fs_mkdir | no | fs.mkdirSync, recursive defaults true, refuses a grant root as target |
| fs_move | no | fs.renameSync, both endpoints validated, refuses a grant root as destination |
| fs_delete | no | fs.unlinkSync (symlinks/files) or fs.rmSync recursive (directories), 10000-entry cap |

relay's `access: read` grant admits only tools with `readOnlyHint: true` (exact-key lookup; absent/null/malformed reads as mutating), so this split is what makes a read-only profile a one-field decision instead of an `allowed_tools` list an operator has to keep correct by hand. `destructiveHint`/`idempotentHint` are not consulted by relay -- don't rely on them for gating.

### fs_bash removal

`fs_bash` (arbitrary shell, `readOnlyHint: false`, `openWorldHint: true`) is gone, not fixed. `allowed_dirs` was never a boundary for it -- a command reaches any path with or without a `cd` -- and every containment guarantee the rest of this server makes was void while it was registered. Removing it also removed the module-level `currentCwd`, the only cross-call mutable state fsmcp ever had.

## Key Patterns

- **Tool = module** with `export function register(registry: ToolRegistry)`. Handler signature: `(args, ctx) => MCPCallResult`.
- **ToolContext** carries `allowedDirs`, computed once per call in `main.ts` by `narrowAllowedDirs()` (security.ts) from `_meta.allowed_dirs` (relay per-call context) and `--allowed-dir` CLI flags -- **never** a plain union of the two. See "C1: `_meta` may only narrow" below. It also carries `labels: LabelEntry[]` (types.ts), this call's virtual-space labels for `allowedDirs`, in the same order -- see "Virtual path space (issue #7)" below.
- **contextSchema v2**, declared in `initialize`'s `serverInfo`, alongside `contextSchemaVersion: 2`:
  ```json
  "contextSchema": {
    "allowed_dirs": {
      "type": "array", "items": { "type": "string" },
      "description": "Directories this client may read, search and modify within",
      "scope": "restrict", "source": "operator",
      "applies_to": ["fs_*"], "enumerable": false,
      "disclose": "count"
    }
  }
  ```
  Every keyword here is load-bearing and must stay byte-exact: absent `contextSchemaVersion`, relay parses this as v1 (looks for a field literally named `allowed_dirs`, derives it from the project path) -- and a **remote** access profile has no project path, so a v1 fsmcp cannot be granted to one at all. `source: "operator"` (not `"project_path"`) is the fix: an operator types the roots instead of relay deriving them. `enumerable: false` because fsmcp cannot offer candidate directories without listing the host's filesystem to whatever UI renders them. No `ui` key -- ignored under v2, and it was stale under v1 too. `disclose: "count"` (relay#33, fsmcp#15) governs what relay renders into the scope note it appends to every governed tool's DESCRIPTION -- the last surface still carrying a host path after issue #7, and the one a live Hermes run read the sandbox root out of. Its spelling fails silently in both directions: `"Count"` makes relay refuse the whole schema (every fsmcp tool withheld from every grant), an unrecognised word is ignored and the value renders anyway. A relay predating relay#33 ignores the key and renders the value; fsmcp cannot detect that and does not claim otherwise.
- **C1: `_meta` may only narrow, never widen.** `_meta` is a field relay populates from context configured elsewhere in the chain, but fsmcp cannot verify anything upstream enforced anything, so it treats `_meta.allowed_dirs` as caller-supplied, same as any other wire argument. `narrowAllowedDirs(cliDirs, metaDirs)` implements the whole rule in one place: CLI+meta both set -> **intersection** (each `_meta` dir kept only if it canonicalizes inside some CLI dir; the rest are dropped and reported on the result, not swallowed); CLI set, meta absent -> CLI; CLI absent, meta set -> meta (relay-mediated mode); both absent -> empty, i.e. deny all. "Absent" vs "present but empty" matters and is preserved from `params._meta?.allowed_dirs` through to this function -- collapsing them with `?? []` is what let a plain union stand in for this table before.
- **The dropped-`_meta`-entries report (`main.ts`, appended to every result whose call supplied a `_meta.allowed_dirs` entry that failed the C1 containment check) echoes those entries as raw host-path text, on a SUCCESS result, entirely outside `vpath.ts`'s translation and outside `redactLeakedHostPaths`'s `isError`-scoped backstop (it is appended after both).** That was accepted deliberately, but **the reasoning recorded here for accepting it was wrong on both halves, and the fsmcp#15 review disproved it by running it.** Kept in full because the corrected version is the useful artefact:

The claim was that the echoed entries are "either plain CLI directories or the literal strings a caller's OWN `_meta.allowed_dirs` supplied". Only the second is possible -- `narrowAllowedDirs` (`security.ts`) pushes nothing but `metaDir` values into `droppedMetaDirs`, so a CLI directory can never appear there.

The load-bearing claim was that **a relay-mediated client cannot reach this at all**, on the grounds that relay builds `_meta` wholly server-side from `stored.Context[extID]` and never forwards anything a client sent. The premise is true and the conclusion does not follow. Server-side is not the same as in-scope: if the MCP is registered with `--args --allowed-dir /A` while the profile's `allowed_dirs` also names `/B`, relay sends `["/A","/B"]`, `/B` fails the C1 containment check, and the report echoes **`/B`** -- an operator-configured host path the client was never granted -- on a success result, to a remote client, over the wire. Reproduced:

```
$ printf '%s\n%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"fs_read",
     "arguments":{"file_path":"/d0/a.txt"},
     "_meta":{"allowed_dirs":["/tmp/f2/A","/tmp/f2/B"]}}}' \
  | node dist/main.js --allowed-dir /tmp/f2/A | tail -1
... {"type":"text","text":"[fsmcp: _meta.allowed_dirs entries were dropped because
    they are not contained within any --allowed-dir root: /tmp/f2/B]"}
```

The oracle argument (can a caller confirm a guessed host path by whether it gets dropped?) still stands on its own: over bare stdio the caller is a local principal who can read the disk anyway. What does not stand is the claim that relay-mediated deployments are out of reach. This is a live disclosure surface, `disclose: "count"` does not reach it, and it wants its own issue rather than a note here. The oracle-shaped read of this (can a caller confirm a guessed host path by whether it gets dropped?) is real over bare stdio, and is closed by that access equivalence, not by translation.
- **Virtual path space (issue #7): `vpath.ts` is a translation layer on top of `security.ts`, never a replacement for it.** A client addresses paths as `/<label>/…`, never a host path -- `decodeInboundPath(virtualPath, ctx.labels)` turns that into the exact host-path string every tool has always validated, by literal string concatenation (deliberately not `path.join`, which would lexically collapse a `..` before `canonicalizePath`'s kernel-style walk ever saw it -- see the function's doc). Every tool handler calls this immediately after reading a path ARGUMENT (`file_path`/`path`/`source`/`destination`) and before calling `checkPathV()`/`checkPathNoFollowFinalV()` (vpath.ts wrappers around security.ts's own `checkPath`/`checkPathNoFollowFinal`, which run completely unmodified and still decide -- the wrapper only translates the message). **A `LabelEntry` carries TWO host spellings of its one directory (issue #21): `hostDir`, the literal string the operator or relay wrote, and `realHostDir`, that same directory as security.ts's `canonicalizePath` resolves it.** They differ only when the grant is reached through a symlink, and they are used in opposite directions on purpose -- INBOUND (`virtualToHost`) concatenates `hostDir` and only ever `hostDir`, because handing `security.ts` an already-resolved string would pre-empt the kernel-style walk that is the whole point of `canonicalizePath`; OUTBOUND (`hostToVirtual`) matches both, because a tool that resolves before it emits produces the second spelling and the map has to recognise it. `assignLabels` is the one place in vpath.ts that asks what a path resolves to, and it asks by calling security.ts's own `canonicalizePath` -- the same function `isWithinAnyDir` uses -- rather than growing a resolution rule of its own: the bug being fixed was the outbound map DISAGREEING with security.ts about which strings name the same directory, so the fix has to be to ask security.ts, not to reimplement it.
- **Outbound translation is deliberate, per call site, never a whole-result scan.** An earlier version of this ran every result (success AND error) through a single blanket rewrite in `ToolRegistry.call`, replacing any occurrence of a granted host directory with its label. PR #10 review found that this was too broad in three ways: (1) it scanned `fs_read`'s own file content and `fs_grep`'s content-mode matched lines, so a file whose bytes happened to contain the sandbox's real path came back silently corrupted, not translated -- confirmed with a write-then-read byte round trip; (2) the "not a valid address" refusal echoed the caller's rejected argument, and that echo passed through the same rewrite, so a CORRECT host-path guess came back rewritten to its label while a wrong one came back verbatim -- a working oracle for exactly the thing issue #7 exists to close; (3) it was applied incidentally (fires whenever a result happens to contain a matching substring) rather than as a decision made at each site, which is itself a reason not to lean on it. Fixed by translating each known path at its own construction site instead: `translatePathIn(text, hostPath, labels)` replaces one SPECIFIC, already-known path substring (never a scan for anything host-directory-shaped), `translateResult(result, hostPaths, labels)` applies it across a result for the path(s) a tool handler already has in scope, and `describeError(err, labels)` rebuilds a caught exception's message using Node's own `err.path`/`err.dest` (a `NodeJS.ErrnoException`'s structured properties, not text-mined from `.message`). The decode-refusal message no longer echoes the caller's argument at all. `ToolRegistry.call` keeps a narrow backstop, `redactLeakedHostPaths()` -- scoped to `isError` results ONLY, so it can never touch `fs_read`/`fs_grep`-content success payloads -- which replaces an entire result with a generic "this is a bug" message if a granted host directory somehow still leaked through; an alarm, not a translation mechanism. It scans BOTH spellings of every grant (issue #21): `realHostDir` is as much the granted directory's real path as `hostDir` is, and under a symlinked root it is the spelling a resolved-path leak would actually arrive in, so an alarm that only knew the operator's spelling would have stayed silent on exactly the deployments that issue is about.
- `fs_glob`/`fs_find`/`fs_list` translate each output path individually via `hostToVirtualOrRedact()`, which **redacts** (a placeholder string) rather than emits a path that cannot be mapped to any granted label -- that case would mean a path reached output from outside the grant, which is a bug security.ts's own checks should already have prevented, not a value this layer can make sense of. **Issue #21 is the reason `hostToVirtual` matches both of a label's spellings rather than only the operator's.** Recognising `realHostDir` maps no file `hostDir` did not already map: `canonicalizePath` resolves prefix-first, so `canonicalizePath(hostDir + rest)` and `canonicalizePath(realHostDir + rest)` are the same path for every `rest` -- the two spellings name exactly the same set of files, and a `rest` that escapes the grant through an inner symlink escapes identically through either one and is stopped identically, at the `validatePath` every call site runs BEFORE outbound translation. What it does change is that a resolved-form hit stops coming back as a placeholder. **Do not "fix" a redaction by widening the map until the path is mappable** -- the placeholder is an alarm, and the only reason it was right to silence it here is that the two strings provably denote one directory; if a path is unmappable because it really is somewhere else, the redaction is the correct output and the bug is upstream.
- Labels: `label=/abs/path` in an `allowed_dirs` entry (CLI or `_meta`, stripped by `stripLabels()` before the bare host path ever reaches `narrowAllowedDirs`/`validatePath` -- an unstripped `"label=/x"` is not absolute and would otherwise resolve against fsmcp's own CWD) wins; otherwise `d<N>` by position in the call's *effective* (already narrowed) scope. `_meta.allowed_dirs` and `--allowed-dir` themselves are unchanged: still plain host-path strings, still operator/relay-side.  **A duplicate label refuses the whole call, fail closed** (`assignLabels`, vpath.ts): `virtualToHost` resolves a label with `Array.prototype.find`, which silently returns the first match, so two directories sharing a label would not error on their own -- it would quietly make the second unaddressable and make `fs_glob`/`fs_find`/`fs_grep` report the identical virtual path for two different files, with `fs_read` of that path always landing on the first-registered directory. Reachable from two explicit `label=`s, or from an explicit `label=` colliding with another entry's auto-assigned `d<N>` (`--allowed-dir d1=/x --allowed-dir /y --allowed-dir /z`: `/y` is position 1, so it auto-assigns `d1`, colliding with `/x`'s explicit one -- a shape no operator would predict from their own flags in order). This codebase already refuses this SHAPE of ambiguity elsewhere rather than picking a winner (`fs_edit` on a non-unique `old_string`, `validatePath` on an empty scope), so `assignLabels` returns an `MCPCallResult` refusal instead of `LabelEntry[]` when it detects one, naming both colliding directories -- safe, because both are always either a CLI directory (operator-side) or an already-narrowed `_meta` entry the caller itself supplied, never a third party's path. `main.ts` returns that refusal directly, before `registry.call` ever runs, so every tool fails closed under a colliding configuration, not just an `fs_read` of the ambiguous address. The SAME directory landing on the SAME label twice (a literal duplicate `--allowed-dir`) is redundant, not ambiguous, and is not refused.
- **Scope refusals carry `_meta.scope_violation: true`.** `checkPath()`/`checkPathNoFollowFinal()` (security.ts) wrap `validatePath`/`validatePathNoFollowFinal` and return the ready-made `MCPCallResult` a tool handler should return directly -- `scopeViolationResult()` (types.ts) when the refusal is "outside your scope" (including the empty-scope case), plain `errorResult()` for everything else (bad regex, file not found, malformed path). Relay's audit reads this off a `tool_error` result as a field on that outcome, not a distinct outcome of its own -- it's what lets an operator's audit log tell "the sandbox held" apart from "the tool broke."
- **security.ts** validates paths via `validatePath()` -- resolves symlinks, checks prefix against allowed dirs. Empty allowed dirs = refuse everything (fail closed, not "no restrictions"); an operator who wants unrestricted access passes `--allowed-dir /` explicitly. NUL bytes and paths over `PATH_MAX` are refused up front (`basicPathError`), so they're clean refusals rather than an exception thrown three stack frames into `fs.lstatSync`.
- **Path resolution is component-by-component, not `realpath`-or-lexical.** `canonicalizePath()` walks from the root, follows every symlink in the part that exists, and carries only the not-yet-existing tail lexically. `fs.realpathSync` is all-or-nothing and throws for a path whose last component does not exist -- the ordinary case for `fs_write` -- and the old lexical fallback left symlink components in the string, so a symlink inside an allowed dir pointing outside it let a *new* file be written outside the sandbox. Two things the obvious "realpath the parent" shortcut still gets wrong: `..` must be applied to the resolved path, never collapsed lexically first (`<allowed>/sub/link/../../x` reads as `<allowed>/x` but lands outside -- and `fs.realpathSync` itself normalises `..` lexically, so this leaked *existing* files too), and a **dangling** symlink must be followed via `lstat`/`readlink` rather than treated as absent, because a write through it still creates the file at its target. Do not rewrite this function; extend around it.
- **`validatePathNoFollowFinal()` (C2)** exists for `fs_delete` alone: it canonicalizes `dirname(path)` as usual but re-joins `basename(path)` un-followed, so deleting `<root>/link-out` (a symlink pointing at, say, `/etc`) refuses or succeeds based on the *link* being in scope, never on where it points. `fs_delete` then uses `lstat`/`unlink` on that exact path -- never `stat`, or the same follow happens one line later.
- **A path that resolves to a grant root is not a valid target for any tool that writes, creates or replaces something at it (issue #24).** One rule, two halves, living next to each other in `security.ts` and worded identically (`refusing to <action> an allowed_dir root: <path>`): `refuseAllowedDirRootWrite()` for the write side (`fs_write` "write to", `fs_edit` "edit", `fs_mkdir` "create", `fs_move`'s DESTINATION "move onto") and `refuseAllowedDirRoot()` for the remove side (`fs_delete` "delete", `fs_move`'s `overwrite` branch "overwrite"). Both are called through their `vpath.ts` wrappers (`refuseAllowedDirRootWriteV`/`refuseAllowedDirRootV`) so the refusal names the label, and both ask `resolvesToAllowedDirRoot()`, which compares CANONICALIZED paths -- `/d0`, `/d0/`, `/d0/.`, `/d0/notes/..` and an in-scope symlink pointing back at the root are one case, not five, and none of them is a string comparison against the label. `checkPath()` cannot make this call itself: a root is *inside itself*, so containment passes, correctly. What fails is everything downstream that derives a **sibling** of the target and, for a root, lands it one level up -- `writeFileAtomic`'s `path.dirname(filePath) + "/.<basename>.fsmcp-tmp-<random>"` temp file, `fs_write`'s own `fs.mkdirSync(path.dirname(resolvedPath), { recursive: true })`, and `fs_mkdir`'s `fs.mkdirSync(root, { recursive: true })` creating every missing ancestor of the root. Measured on the broken build: `fs_write { file_path: "/d0", content: <5MB> }` left 5,000,000 bytes of caller-chosen content in the grant's PARENT, with only the closing `rename` failing (`EISDIR`) after the bytes were already on disk outside the grant; with the parent chmod'd `0555` the failure moves to the `open` (`EACCES`), which is what proves the creation was aimed there rather than merely that the call failed. "The temp file is unlinked in `writeFileAtomic`'s `catch`" is not a defence -- cleanup is best-effort, does not run if the process is killed, and the file's size is caller-chosen up to `MAX_WRITE_BYTES` with a caller-influenced name, in what on a real machine is `~/Documents` or `~`. **The write half returns `scopeViolationResult()`, the remove half a plain `errorResult()`, and that asymmetry is deliberate**: servicing a root-addressed write really would have put bytes outside `allowed_dirs` (the sandbox held -- and before this fix `relay audit` showed only a bare `tool_error` carrying someone else's errno, so an operator reading the log had no way to see that a file had been created outside the granted directory), whereas refusing to *delete* the root removes only something inside the grant and is "the sandbox must survive its occupant", not "you addressed something out of scope" -- and `_meta.scope_violation` must mean only the latter. `fs_mkdir` refuses the resolved root whether or not it currently exists, rather than only when it would create something: an existence-conditional rule would be a second, weaker copy of the same rule decided by a race-able `stat`, and "your grant root already exists" was never a useful answer. **The caller-side refusal is the whole fix today.** `writeFileAtomic` asserting that `path.dirname(filePath)` is in scope is worth having as defence in depth and is deliberately not in this change (that file is being rewritten elsewhere); until it lands, these call sites are the only thing between a root-addressed write and the parent directory, so do not remove one without adding that assert first.
- **Tool output that is a path is re-validated.** `fs_glob`, `fs_find` and `fs_grep` all filter every hit through `validatePath` rather than trusting descendants of a validated directory: whatever walks the tree chooses what gets reported, so a symlink inside an allowed directory that points outside it can come back as an in-scope-looking path. `fs_list` does not recurse, so it has no such gap: every entry it reports is `path.join(validatedDir, entry.name)` for a name `readdir` produced, which cannot contain a separator or `..`.
- **`fs_glob` walks from a RESOLVED root (issue #21), and that is the only thing about the walk that changed.** `globSync`'s default `follow: false` does not merely decline to follow links inside the tree -- it will not walk THROUGH a `cwd` that is itself a symlink, so a recursive `**` pattern against a grant reached through a link (`/tmp` on macOS, a relocated home, an external volume, a cloud-storage alias -- none of which an operator has to have thought about) returned **an empty success**: the client was told the folder was empty and `relay audit` recorded `ok`, which is the one shape this stack's runbook says must never happen. A pattern whose first component is a literal (`sub/*.txt`) sidesteps the `**` walk and worked, which made the failure look intermittent rather than total; `fs_find`, `fs_grep` and `fs_list` were unaffected. The fix is `canonicalizePath(dir)` (security.ts, the only resolver here, and the same one `isWithinAnyDir` uses to decide what "inside this grant" means) as the `cwd` handed to `globSync`. **`follow: true` is not the fix and was measured: it does not resolve a symlinked `cwd` at all, and it would additionally make glob follow every link INSIDE the tree -- precisely the traversal the per-hit re-validation above exists to catch.** Resolving the root changes where the walk starts and nothing about what it is willing to walk through: every symlink under the root is still un-followed and every hit still goes through the real, unmodified `validatePath` (measured against the fix: with `escape_file.txt -> <outside>/secret.txt` inside a symlinked root, `**/*.txt` genuinely returns that link from `globSync` and `validatePath` genuinely drops it). A root that will not resolve at all is skipped -- what `isWithinAnyDir` does with the same case, for the same reason -- and if that leaves nothing to search the result is an ERROR about the directory, never an empty success. Note the pairing: **canonicalising the walk is necessary and, on its own, actively worse.** Applied alone against `main`, every hit comes back spelled with the resolved root, matches no label's `hostDir`, and the caller gets a page of `[fsmcp: path outside the granted directories -- redacted]` instead of a page of filenames -- an empty answer traded for a false alarm. The outbound half (`hostToVirtual` matching both spellings, above) is not optional, and `tests/symlinked-root.test.js` pins both halves independently so neither can be reverted quietly.
- **`fs_glob`'s `pattern` is validated before it reaches the filesystem, and a pattern may not name a LOCATION (issue #25).** `pattern` was the one path-shaped input in this server that never went through `decodeInboundPath`/`checkPathV`, and `globSync` ignores `cwd` completely for an absolute pattern -- so `pattern` was a host-path traversal primitive that the validated `path` argument did not bound. The per-hit `validatePath` filter held (no name and no byte from outside the grant was ever emitted), which is precisely what made this hard to see: **what escaped was not data, it was answers.** `<grant>/**` returned hits, one character wrong returned an empty string, and `?`/`*`/`[a-r]` turn that difference into a character-by-character search of the host's layout -- the capability issue #7 exists to remove, handed back by the only tool that takes a pattern. **Output filtering cannot close an oracle whose signal IS the empty output**, which is why this is a check on the input and not a better filter on the results. Two more consequences fell out of the same root: naming somewhere out of scope was an empty SUCCESS (`{"pattern":"/etc/…"}` -> `ok`, `""`), making fs_glob the only tool here where addressing something outside the grant was not a refusal; and the walk was unbounded, so one call could walk `/System/Library` while every OTHER client of the same shared, synchronous child waited. The rule all three collapse to: **a pattern is a pattern, not an address.** The address is the `path` argument, which is already decoded from the virtual space and already validated; a pattern may only describe names UNDERNEATH it. So, before a single syscall: an absolute pattern is refused, a `..` component is refused, and both are `scopeViolationResult` (same classification `decodeInboundPath` gives "you did not name anything in fsmcp's address space", same reason -- a caller that cannot spell an address inside its grant is naming something outside it), with **no echo of the pattern**, because a refusal that varies with its input is the same oracle one level up. A NUL in a pattern is a plain `errorResult` -- malformed input, not a scope violation, matching `basicPathError`'s treatment of the same byte in a path.
  - **Both checks are deliberately conservative regexes over the raw pattern, not an expansion of it.** Brace alternatives really can hide either shape -- measured against the raw library, `{/etc,sub}` with a wildcard below it returns `/etc/hosts`, and `{sub,..}` with one returns the search directory's parent -- and `path.isAbsolute` sees neither. The exact test would be to brace-expand the way `glob` does, which means either importing `minimatch` (a transitive dependency, not a declared one -- `glob` stays the only runtime dep) or hand-writing an expander that has to agree with someone else's parser forever. A containment rule that tracks another package's grammar is a hole waiting for a version bump, so instead: `..` is matched as a TOKEN at any component boundary (`^`, `$`, `/`, `{`, `}`, `,`) and a `/` immediately after `{` or `,` is treated as an absolute alternative. This over-refuses a couple of exotic literals (a pattern with escaped braces around a genuine `..` filename) and fails in the safe direction; it deliberately does NOT try to catch a `..` produced by a magic component, because Node's `readdir` never reports `.` or `..` as entries, so only a literal `..` component can climb.
  - **A `..` that would have stayed inside the grant is refused too, and that is the decision, not an oversight.** A path ARGUMENT containing `..` is accepted and resolved -- `canonicalizePath` walks it kernel-style and the containment check decides. A PATTERN cannot get the same treatment: a pattern with a wildcard before the `..` does not resolve to one path, so there is nothing to hand the containment check. Resolving patterns "where possible" would mean two rules with a boundary between them that a caller can probe, which is how the oracle came back last time. Every directory in scope is addressable by naming it with `path`.
  - **The walk is bounded by the shared `grepBudgetMs()`, enforced through glob's `ignore` hook.** The 1000-result cap bounds the OUTPUT, not the traversal: a pattern that matches nothing walks everything and returns an empty list having done all the work. Checking the clock between yielded results does not work either -- a pattern that matches nothing yields nothing to check between -- so the budget rides on `ignored`/`childrenIgnored`, which glob calls as it descends whether or not anything matches, and `childrenIgnored` prunes a subtree outright. Measured: a globstar over `/System/Library` now returns at the budget, to the millisecond. A cut-short walk **says so** and, when it found nothing at all, says only that -- an incomplete answer that reads as a complete one is the same failure as #21's empty success. `fs_glob` reuses fs_grep's and fs_find's budget rather than inventing a third: the hazard is "one synchronous process serves every caller", a property of the server, not of a tool.
  - **#21 and #25 interact and were fixed together.** #21 teaches the outbound map the RESOLVED spelling of a grant; on its own that widens #25's oracle by one spelling, because an absolute pattern naming the real target of a symlinked grant began mapping to real `/d0/...` paths where it previously came back redacted. #25's refusal closes both spellings before the walk. Pinned by a test in `tests/glob-pattern-scope.test.js` that grants a symlinked root and refuses an absolute pattern in either form.
- **fs_grep** shells out to `rg` if available, falls back to recursive readdir + RegExp; both paths are bounded by `grepBudgetMs()` and both re-validate every path before it reaches the caller. The `rg` path always passes `--json` (never `-l`/`-c`/`-n`), parsed by `formatRgJson()`: issue #7 needed something to reliably split "this substring is the path" from "this substring is the file's own content" in order to translate only the former, and the old plain-text parsing (`path:line:content`, regex-anchored on the numeric line number because content can itself contain colons) was already flagged as fragile for an unusual filename -- building a rewrite step on that fragility would have made it load-bearing in a new way. `--json` gives the split structurally (`data.path.text` vs `data.lines.text`) instead. `-c`/count cannot be combined with `--json` (verified against a real ripgrep: it silently reverts to `-c`'s own plain output), so count is derived from each file's `end` event (`stats.matched_lines`) instead. The Node fallback (`grepFallback`) builds its own output strings from paths it already controls, so it needs no JSON round-trip -- but it does need `hostToVirtualOrRedact` on every path it emits (an optional `labels` parameter, threaded from `ctx.labels` at the real call site and left `undefined` for the ReDoS-budget unit tests that have no concept of labels at all). An earlier version of this reasoned that `ToolRegistry.call`'s generic outbound pass (`redactLeakedHostPaths`) would cover it instead; that pass is scoped to `isError` results only (see "Outbound translation is deliberate" above), and an ordinary successful search is never an error result, so the sandbox's real absolute path came back unmodified in every output mode on any host without ripgrep on PATH -- fixed by translating each path at grepFallback's own three emission sites, the same as everywhere else in this file. Matched line TEXT in content mode (`lines[idx]`) is never touched, for the same reason `formatRgJson`'s `lines.text` and `fs_read`'s own bytes are not. **`grepWithRg`'s catch-all error branch (`grep error: ${detail}`, built from `rg`'s own `stderr`/`.message` text) is a known, accepted exception to "every path goes through `describeError`": ripgrep's free-text errors are not structurally split into path/content the way `--json` output is, so there is no `.path`-shaped field to translate, and correctness here currently leans entirely on `redactLeakedHostPaths`'s `isError`-scoped backstop catching a granted directory if `rg` happens to print one verbatim (confirmed live: a stub `rg` erroring with the sandbox root in its stderr came back redacted, not leaked). That is a real gap, not a false alarm -- if a later change adds a new `rg` flag (`--follow`, a new output mode, anything that changes what `rg` writes to stderr on failure) whose error text could embed a host path in a shape the backstop's exact-substring match does not catch, this branch is where that leak would resurface. Parsing ripgrep's own error text to close it is exactly the fragility this file moved off of when `--json` replaced plain-text output for matches; treat any change here as a reason to re-verify this specific branch against a real failing `rg`, not as license to assume the backstop always saves it.**
- **fs_find** = `rg --files --no-follow` (Node walker fallback, which skips every symlink outright) + in-process fzf-style subsequence scoring (contiguity + word-boundary bonuses) over the resulting, re-validated file list. No new dependency -- `glob` stays the only runtime one. `fs_find` and `fs_grep` are correct under a symlinked root (issue #21) **for a reason neither of them chose**: `rg` echoes back the unresolved directory string it was handed, and the Node fallbacks build their paths with `path.join` from that same string, so what they emit happens to be spelled the way `hostToVirtual` used to require. Since issue #21 that is no longer load-bearing -- the outbound map recognises either spelling -- but it was never pinned before, so `tests/symlinked-root.test.js` now pins both tools under a symlinked root as well as `fs_glob`. If either ever starts emitting resolved paths (a new `rg` flag, an output-mode change, a fallback rewrite that realpaths), the mapping already handles it and the tests say so.
- **fs_edit** uses `split().join()` for literal matching (no regex special char issues), and refuses a `file_path` that resolves to a grant root before it reads anything (issue #24). Nothing reached `writeFileAtomic` for a root here even before that check -- `fs.readFileSync` of a directory throws `EISDIR` and the handler answered "file not found" -- but that was an accident of ordering, dependent on a read failing first for an errno nothing here inspects, and "file not found" is the wrong answer for a path that exists and is the caller's own grant root.
- **Byte fidelity is content-based, not extension-based (issue #11).** `fs.readFileSync(path, 'utf-8')` -- the call every one of `fs_read`/`fs_edit`/`fs_grep`'s fallback used -- maps every byte that is not valid UTF-8 to U+FFFD before any of this codebase's own code runs. That mapping is lossy and irreversible the instant it happens: the original byte is gone, and writing the decoded string back (`fs_write`, `fs_edit`) re-encodes each replacement character as three DIFFERENT bytes, silently corrupting the file with no error, warning, or hint anywhere in the path (measured: 4 bytes of latin-1 became 10; 7 bytes of arbitrary binary became 13). The fix is a pass-through principle, not a content judgement: fsMCP does not decide what a file's bytes MEAN -- there is no "this looks like a binary file" heuristic anywhere in this codebase, and in particular no extension-keyed special case (an earlier version of `fs_read` auto-base64'd a fixed set of image extensions; that keyed the decision off a **string**, so two files with byte-identical content and different names behaved differently, and every other non-image binary -- a `.dat`, a latin-1 `.txt`, a UTF-16 file -- still took the lossy path. Removed entirely, not extended, because extending it would mean picking a bigger fixed list instead of fixing the actual question). Instead, every call site that needs to decide asks one question, from the bytes: "can the caller's DECLARED encoding represent these bytes losslessly?" `src/encoding.ts`'s `decodeUtf8Strict()` (`new TextDecoder('utf-8', { fatal: true })`, never `Buffer#toString('utf-8')`, which has no strict mode and is the exact lossy call this issue is about) answers that for UTF-8 text; a hand-rolled byte scanner is deliberately not used in its place, since it would duplicate logic the platform already implements correctly with real ways to get it subtly wrong (an off-by-one on a continuation byte, an overlong encoding accepted). `fs_read` takes an `encoding` argument: `"text"` (default) decodes as UTF-8 and refuses if that fails, naming the file and pointing at `"base64"`; `"base64"` returns the file's exact bytes unconditionally, on any file, decoded or not. `fs_read`'s text mode was already a VIEW before this issue (line-numbered, truncated at 2000 chars per line, `offset`/`limit`-windowed) and is documented as one now rather than implied to be byte-faithful; those view options are meaningless against a byte dump, so `encoding: "base64"` REFUSES `offset`/`limit` rather than silently ignoring them, and returns whole-file bytes with no line numbers and no truncation. **A mode that exists for fidelity must round-trip through itself** (PR #13 review): `fs_read`'s base64 reply (`src/tools/read.ts`) is the BARE base64 payload -- no header, no trailing newline, nothing else in the content string, with the byte count carried structurally in `_meta.bytes` instead -- specifically so `fs_read(base64)` piped straight into `fs_write(base64)`'s `content`, unmodified, is an identity on the file's bytes. An earlier version prefixed a human-readable `"[base64: N bytes]\n"` header; that failed closed rather than corrupting anything (`isValidBase64` refused the header line as malformed base64), but it meant fs_read's own reply was not valid fs_write input, so the obvious composition of the two calls didn't work -- and a caller that "fixed" this by guessing at an unspecified stripping pattern could just as easily strip it wrong and silently corrupt the bytes, reproducing this issue's core failure one level up, looking like a caller bug instead of a design one. Text mode is explicitly exempt from this rule -- it is a documented view (line-numbered, truncated, says so) and never claimed to be an identity. `fs_write` mirrors this: `encoding: "text"` (default, unchanged) writes the UTF-8 encoding of `content` as-is; `encoding: "base64"` decodes `content` as base64 and writes those exact raw bytes (`fs.writeFileSync` with no encoding argument -- passing `'utf-8'` there would re-interpret an arbitrary byte buffer as text, corrupting exactly what this path exists to preserve), after `isValidBase64()` rejects anything outside the base64 alphabet or not block-aligned (Node's own base64 decoder is lenient and silently DROPS invalid characters rather than erroring, which would otherwise let a truncated copy-paste decode to the wrong bytes and still report success). **`fs_write` does NOT refuse U+FFFD in text-mode content** -- a file may legitimately contain the replacement character, and second-guessing the caller's own declared-text content is a content judgement this principle forbids, not a representability question; if a caller writes U+FFFD, that is written, verbatim, like any other character. **A lone (unpaired) UTF-16 surrogate in `content`/`new_string` (possible over JSON-RPC -- `JSON.parse` does not validate surrogate pairing, so a wire string can contain one even though nothing this server itself ever decodes from disk can produce one) IS refused unconditionally, by both `fs_write` and `fs_edit`, with no escape hatch**: this is not a heuristic, because there is no valid UTF-8 encoding for a surrogate code point at all -- Node's encoder would silently substitute U+FFFD for it, the same lossy shape as the rest of this issue, just introduced at the JSON-RPC boundary instead of by a disk read, and refusing has no legitimate case to second-guess since representing it correctly is not possible in the first place. `fs_edit` refuses to operate on a file whose bytes are not valid UTF-8 at all (no base64 mode for it -- a byte-level splice is not a string replacement, and this file does not invent a new operation to paper over that): it is defined over text, and content that is not representable as text has no meaning to find-and-replace against, so refusing is "this operation does not apply," not "binary is dangerous." `fs_grep`'s Node fallback (`grepFallback`) reads with the same `decodeUtf8Strict()` and skips (does not error on) a file that fails it, the same as any other unreadable file -- it only reports, never writes, so there is no write-back to corrupt, but reporting a match against a lossily-substituted line would still hand a caller text that does not match the file with no way to tell; skipping keeps it agreeing with `fs_read` about what it declines to decode. Truncation of an over-long line is flagged twice: the existing inline `"... [truncated]"` marker for a human reader, and `_meta.truncated: true` on the result for a caller that wants to branch on it programmatically instead of pattern-matching English -- a sibling of `_meta.scope_violation` (see below), not a replacement for it; the two never appear on the same result (one is a refusal's `_meta`, the other a success's).
- **fs_move** validates both `source` and `destination` independently and in full (C4), refuses a `destination` that resolves to a grant root at all (issue #24 -- checked up front, before the exists/`overwrite` branching, so a root destination has one answer instead of three depending on whether the root exists and whether `overwrite` was set), refuses an existing destination unless `overwrite: true`, and refuses moving a directory into (or onto) its own descendant. The older `refuseAllowedDirRoot` guard in the `overwrite` branch is now unreachable and kept on purpose: it is the remove half of the rule guarding the `rmSync` on the next line, and it must stay true that that syscall cannot be reached with a root in hand.
- **fs_delete** refuses to remove an `allowed_dir` root itself (the remove half of the grant-root rule above -- same words, deliberately NOT a `scope_violation`), defaults `recursive` to `false`, caps a recursive delete at 10,000 entries (refusing past it rather than truncating silently), and relies on `fs.rmSync`'s recursive mode unlinking a symlink it meets rather than following it -- pinned by test, not just assumed.
- **TOCTOU is a documented non-goal (C7),** for every mutating tool including the new ones: winning the check-then-use race requires writing a symlink inside an allowed directory, which the same uid running fsmcp could already do directly. If fsmcp ever runs more privileged than whoever can write into an allowed dir, the fix is `openat`-per-component with `O_NOFOLLOW` from a pinned root fd, not a better check.
- **No throws across tool boundary** -- registry wraps handlers in try/catch as a backstop, but tools are expected to check cleanly (absolute path, NUL bytes, overlong paths -- all centralized in `security.ts`) rather than lean on the catch.

## Adding a Tool

1. Create `src/tools/foo.ts`
2. Export `registerFoo(registry: ToolRegistry)`
3. Define tool with `registry.register({ name, description, inputSchema, category, annotations }, handler)` -- `annotations: { readOnlyHint, openWorldHint }` is required on the type, not optional; set both explicitly and honestly
4. Use `schema()`, `stringProp()`, `intProp()`, `boolProp()`, `enumProp()` from registry. For any path ARGUMENT's description (`file_path`/`path`/`source`/`destination`), use `virtualPathDescription()` (registry.ts) instead of writing your own -- it is the one place that describes the `/<label>/...` address shape without asserting a concrete label (labels are assigned per call, not known when this static schema is built), and every existing tool's path argument goes through it so they stay worded identically. Writing "Absolute path to the file" by hand here is the exact regression a schema-text test (`tests/schema-text.test.js`) exists to catch: that was true before issue #7 and became actively misleading after it.
5. Return via `textResult()` or `errorResult()` from types; use `scopeViolationResult()` (or `checkPath()`/`checkPathNoFollowFinal()` from security.ts, which return it for you) for any refusal that means "outside your scope". If the tool WRITES, CREATES or REPLACES anything at a caller-supplied path, `checkPathV()` alone is not enough -- a grant root passes it, because a root is inside itself -- so also call `refuseAllowedDirRootWriteV(hostPath, ctx.allowedDirs, '<verb>', ctx.labels)` (vpath.ts) on that path, immediately after the containment check and before any syscall (issue #24)
6. Accept `ToolContext` as second arg. For any path ARGUMENT the client supplies, call `decodeInboundPath(arg, ctx.labels)` (vpath.ts) first and use the host path it returns -- not the raw argument -- for everything after. Check that decoded host path with `checkPathV()`/`checkPathNoFollowFinalV()` (vpath.ts) -- not `checkPath()`/`checkPathNoFollowFinal()` (security.ts) directly, or the refusal message will still name the host path, and not `validatePath()` + `errorResult()` by hand, or the refusal won't carry `_meta.scope_violation` when it should. A path the tool itself PRODUCES (a search hit, a directory listing entry) needs `hostToVirtualOrRedact()` (vpath.ts) on the way out. Any OTHER message that embeds a path this handler already decoded (a success sentence, a `file not found`) must be wrapped in `translateResult(result, [thatPath, ...], ctx.labels)` before it is returned -- outbound translation is deliberate per call site, not automatic (see "Outbound translation is deliberate" above); a caught exception's message should go through `describeError(err, ctx.labels)` instead of `err.message` directly, so `err.path`/`err.dest` get translated. Never pass a tool's own file CONTENT (what `fs_read` returns, or a matched line in `fs_grep` content mode) to any of these -- it is not a path, and translating it would corrupt it (PR #10)
7. Import and call `registerFoo(registry)` in `main.ts`
