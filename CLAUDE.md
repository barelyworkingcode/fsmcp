# fsMCP

MCP server providing file system tools via stdio. 10 tools, 1 category. TypeScript/Node.js. One runtime dependency (glob). No shell: nothing here reaches `execSync` or a shell string; `execFileSync` with an argv array is the only way this process ever spawns anything -- ripgrep (PATH-resolved, optional, for `fs_grep` and `fs_find`) and `/bin/cp` (absolute, for the metadata-preserving half of the atomic replace in `atomicWrite.ts`, and the only spawn in this tree that writes).

## Architecture

Single-threaded stdin/stdout MCP server. Newline-delimited JSON-RPC 2.0. Protocol version `2024-11-05`.

```
src/
  main.ts        Stdin loop, JSON-RPC dispatch (initialize, tools/list, tools/call), _meta narrowing (C1)
  types.ts       Wire types, MCPTool interface, result helpers (textResult, errorResult, scopeViolationResult)
  registry.ts    ToolRegistry class + JSON schema builder helpers
  security.ts    Path validation against allowed_dirs (_meta + CLI flags), _meta narrowing rule
  limits.ts      Wire/context bounds (issue #19): response bytes, base64 file ceiling, exact JSON-escaped sizing, the every-result backstop
  vpath.ts       Virtual <-> host path translation (issue #7), layered on top of security.ts, never inside it
  resultFormat.ts  How line-oriented text results are shaped (issues #31, #37): the path-field escaping, the sentence that states its rules, the results-end-at-the-first-blank-line rule
  tools/         One file per tool, each exports register(registry)
```

Entry point reads stdin line-by-line, dispatches to `ToolRegistry`, writes JSON to stdout. Synchronous.

## Tools

All ten tools are category "File System" -- there is no second category any more (the old "Shell" category, and `fs_bash` with it, is gone: see "fs_bash removal" below).

| Tool | Read-only | Backend |
|------|-----------|---------|
| fs_read | yes | text: fs.readFileSync (raw bytes), strict UTF-8 decode, cat -n, byte-bounded paging. base64: positional read of a byte window |
| fs_glob | yes | glob npm package, relative patterns only (refusal derived from glob's own parser), walk pruned to the grant through glob's `ignore` hook, mtime sort, escaped path per line, 1000-result + byte cap, wall-clock budget |
| fs_grep | yes | ripgrep (rg) with Node.js fallback, wall-clock budget, escaped path field (`:` included) with verbatim content, 1000-line + 1MiB result cap |
| fs_list | yes | fs.readdirSync, one directory, non-recursive, 5000-entry cap, escaped path field, symlink size 0 |
| fs_find | yes | `rg --files --no-follow --null` (Node walker fallback) + in-process fuzzy scoring, escaped path per line, 200-result + byte cap |
| fs_write | no | fs.writeFileSync (text or base64 bytes), auto-creates parent dirs INSIDE an existing grant root, refuses a grant root as target, 1MiB inbound `content` cap |
| fs_edit | no | split/join literal string replacement, UTF-8 text only, refuses a grant root as target, refuses an empty or unchanged old_string, 1MiB inbound cap on `old_string`/`new_string` and a 10MiB read cap |
| fs_mkdir | no | fs.mkdirSync, recursive defaults true, refuses a grant root as target and a grant root that does not exist |
| fs_move | no | fs.renameSync and nothing else -- no unlink, ever -- both endpoints validated, refuses a grant root at EITHER end, reports a same-inode pair as such rather than as a move |
| fs_delete | no | fs.unlinkSync (symlinks/files) or fs.rmSync recursive (directories), 10000-entry cap |

relay's `access: read` grant admits only tools with `readOnlyHint: true` (exact-key lookup; absent/null/malformed reads as mutating), so this split is what makes a read-only profile a one-field decision instead of an `allowed_tools` list an operator has to keep correct by hand. `destructiveHint`/`idempotentHint` are not consulted by relay -- don't rely on them for gating.

### fs_bash removal

`fs_bash` (arbitrary shell, `readOnlyHint: false`, `openWorldHint: true`) is gone, not fixed. `allowed_dirs` was never a boundary for it -- a command reaches any path with or without a `cd` -- and every containment guarantee the rest of this server makes was void while it was registered. Removing it also removed the module-level `currentCwd`, the only cross-call mutable state fsmcp ever had.

## Key Patterns

- **Tool = module** with `export function register(registry: ToolRegistry)`. Handler signature: `(args, ctx) => MCPCallResult`.
- **ToolContext** carries `allowedDirs`, computed once per call in `main.ts` by `narrowAllowedDirs()` (security.ts) from `_meta.allowed_dirs` (relay per-call context) and `--allowed-dir` CLI flags -- **never** a plain union of the two. See "C1: `_meta` may only narrow" below. It also carries `labels: LabelEntry[]` (types.ts), this call's virtual-space labels for `allowedDirs`, in the same order -- see "Virtual path space (issue #7)" below.
- **contextSchema v2**, declared in `initialize`'s `serverInfo`, alongside `contextSchemaVersion: 2`:
  ```json
  "contextSchema": {
    "allowed_dirs": {
      "type": "array", "items": { "type": "string" },
      "description": "Directories this client may read, search and modify within",
      "scope": "restrict", "source": "operator",
      "applies_to": ["fs_*"], "enumerable": false,
      "disclose": "count"
    }
  }
  ```
  Every keyword here is load-bearing and must stay byte-exact: absent `contextSchemaVersion`, relay parses this as v1 (looks for a field literally named `allowed_dirs`, derives it from the project path) -- and a **remote** access profile has no project path, so a v1 fsmcp cannot be granted to one at all. `source: "operator"` (not `"project_path"`) is the fix: an operator types the roots instead of relay deriving them. `enumerable: false` because fsmcp cannot offer candidate directories without listing the host's filesystem to whatever UI renders them. No `ui` key -- ignored under v2, and it was stale under v1 too. `disclose: "count"` (relay#33, fsmcp#15) governs what relay renders into the scope note it appends to every governed tool's DESCRIPTION -- the last surface still carrying a host path after issue #7, and the one a live Hermes run read the sandbox root out of. Its spelling fails silently in both directions: `"Count"` makes relay refuse the whole schema (every fsmcp tool withheld from every grant), an unrecognised word is ignored and the value renders anyway. A relay predating relay#33 ignores the key and renders the value; fsmcp cannot detect that and does not claim otherwise.
- **C1: `_meta` may only narrow, never widen.** `_meta` is a field relay populates from context configured elsewhere in the chain, but fsmcp cannot verify anything upstream enforced anything, so it treats `_meta.allowed_dirs` as caller-supplied, same as any other wire argument. `narrowAllowedDirs(cliDirs, metaDirs)` implements the whole rule in one place: CLI+meta both set -> **intersection** (each `_meta` dir kept only if it canonicalizes inside some CLI dir; the rest are dropped and reported on the result, not swallowed); CLI set, meta absent -> CLI; CLI absent, meta set -> meta (relay-mediated mode); both absent -> empty, i.e. deny all. "Absent" vs "present but empty" matters and is preserved from `params._meta?.allowed_dirs` through to this function -- collapsing them with `?? []` is what let a plain union stand in for this table before.
- **The dropped-`_meta`-entries report (`main.ts`, appended to every result whose call supplied a `_meta.allowed_dirs` entry that failed the C1 containment check) tells the client the FACT and the COUNT; the entries themselves go to stderr, for the operator.** Fixed in issue #30/#26's cluster; the reasoning below is kept in full because the history is the useful artefact. It used to echo those entries as raw host-path text, on a SUCCESS result, entirely outside `vpath.ts`'s translation and outside `redactLeakedHostPaths`'s `isError`-scoped backstop (it is appended after both). That was accepted deliberately, but **the reasoning recorded here for accepting it was wrong on both halves, and the fsmcp#15 review disproved it by running it.**

The claim was that the echoed entries are "either plain CLI directories or the literal strings a caller's OWN `_meta.allowed_dirs` supplied". Only the second is possible -- `narrowAllowedDirs` (`security.ts`) pushes nothing but `metaDir` values into `droppedMetaDirs`, so a CLI directory can never appear there.

The load-bearing claim was that **a relay-mediated client cannot reach this at all**, on the grounds that relay builds `_meta` wholly server-side from `stored.Context[extID]` and never forwards anything a client sent. The premise is true and the conclusion does not follow. Server-side is not the same as in-scope: if the MCP is registered with `--args --allowed-dir /A` while the profile's `allowed_dirs` also names `/B`, relay sends `["/A","/B"]`, `/B` fails the C1 containment check, and the report echoes **`/B`** -- an operator-configured host path the client was never granted -- on a success result, to a remote client, over the wire. Reproduced:

```
$ printf '%s\n%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"fs_read",
     "arguments":{"file_path":"/d0/a.txt"},
     "_meta":{"allowed_dirs":["/tmp/f2/A","/tmp/f2/B"]}}}' \
  | node dist/main.js --allowed-dir /tmp/f2/A | tail -1
... {"type":"text","text":"[fsmcp: _meta.allowed_dirs entries were dropped because
    they are not contained within any --allowed-dir root: /tmp/f2/B]"}
```

The oracle argument (can a caller confirm a guessed host path by whether it gets dropped?) still stands on its own: over bare stdio the caller is a local principal who can read the disk anyway. What does not stand is the claim that relay-mediated deployments are out of reach. That made it a live disclosure surface that `disclose: "count"` does not reach, and it got its own issue (fsmcp#26).

**The fix, and why it had to be at the point of production rather than behind a backstop.** No backstop can reach this even in principle: **a dropped directory is by construction not in `ctx.labels`**. `redactLeakedHostPaths` works by knowing the granted roots and matching against them, so widening it past `isError` (which would reintroduce the PR #10 content-corruption hazard for nothing) still would not catch a path that is precisely one that was NOT granted -- there is nothing to translate it to. The message simply has to stop naming the path.

So `main.ts` now splits it the way `assignLabels`' duplicate-label refusal already does: **stderr gets the detail** (the entries, in full, on the stream a stdio MCP's host collects a child's diagnostics on, which is not the protocol stream and cannot corrupt a response) because the operator is the only party who can reconcile a CLI floor with a profile and the only one entitled to the paths; **the client gets the fact and the count** (`"...entries were dropped because they are not contained within any --allowed-dir root -- N of them"`), for the same reason `disclose` is `"count"` and not `"none"`: an agent that cannot see that it is confined behaves worse, not better, but it does not need the host's directory layout to know its effective scope is narrower than the one it was sent. The client can do nothing with the paths in any case -- it cannot fix a registration.

**Deliberately a note, not a refusal**, which is where this parts company with the duplicate-label case it otherwise copies. The two look alike and are not. A duplicate label leaves the address space with **no correct reading** -- a `/<label>/…` path names two different files, and picking one hands a caller the wrong file's bytes -- so refusing every call is the only answer that is not a guess. This narrowing has exactly one reading, it is the one C1's own table specifies, and it is already fail-closed: the effective scope is the intersection, which is the safe end of the disagreement, not a coin flip between two. Refusing would turn an operator's over-tight CLI floor into a total outage of a capability whose surviving grant is still valid, and it would fire on the ordinary intended shape of "the operator tightened the floor". If this ever needs to be louder, the levers are the stderr line and relay's own scope note -- which currently renders the profile's count rather than the effective one, and is filed against relay -- not a refusal fsmcp cannot tell apart from correct use.
- **Virtual path space (issue #7): `vpath.ts` is a translation layer on top of `security.ts`, never a replacement for it.** A client addresses paths as `/<label>/…`, never a host path -- `decodeInboundPath(virtualPath, ctx.labels)` turns that into the exact host-path string every tool has always validated, by literal string concatenation (deliberately not `path.join`, which would lexically collapse a `..` before `canonicalizePath`'s kernel-style walk ever saw it -- see the function's doc). Every tool handler calls this immediately after reading a path ARGUMENT (`file_path`/`path`/`source`/`destination`) and before calling `checkPathV()`/`checkPathNoFollowFinalV()` (vpath.ts wrappers around security.ts's own `checkPath`/`checkPathNoFollowFinal`, which run completely unmodified and still decide -- the wrapper only translates the message).
- **Outbound translation is deliberate, per call site, never a whole-result scan.** An earlier version of this ran every result (success AND error) through a single blanket rewrite in `ToolRegistry.call`, replacing any occurrence of a granted host directory with its label. PR #10 review found that this was too broad in three ways: (1) it scanned `fs_read`'s own file content and `fs_grep`'s content-mode matched lines, so a file whose bytes happened to contain the sandbox's real path came back silently corrupted, not translated -- confirmed with a write-then-read byte round trip; (2) the "not a valid address" refusal echoed the caller's rejected argument, and that echo passed through the same rewrite, so a CORRECT host-path guess came back rewritten to its label while a wrong one came back verbatim -- a working oracle for exactly the thing issue #7 exists to close; (3) it was applied incidentally (fires whenever a result happens to contain a matching substring) rather than as a decision made at each site, which is itself a reason not to lean on it. Fixed by translating each known path at its own construction site instead: `translatePathIn(text, hostPath, labels)` replaces one SPECIFIC, already-known path substring (never a scan for anything host-directory-shaped), `translateResult(result, hostPaths, labels)` applies it across a result for the path(s) a tool handler already has in scope, and `describeError(err, labels)` rebuilds a caught exception's message using Node's own `err.path`/`err.dest` (a `NodeJS.ErrnoException`'s structured properties, not text-mined from `.message`). The decode-refusal message no longer echoes the caller's argument at all. `ToolRegistry.call` keeps a narrow backstop, `redactLeakedHostPaths()` -- scoped to `isError` results ONLY, so it can never touch `fs_read`/`fs_grep`-content success payloads -- which replaces an entire result with a generic "this is a bug" message if a granted host directory somehow still leaked through; an alarm, not a translation mechanism.
- `fs_glob`/`fs_find`/`fs_list` translate each output path individually via `hostToVirtualOrRedact()`, which **redacts** (a placeholder string) rather than emits a path that cannot be mapped to any granted label -- that case would mean a path reached output from outside the grant, which is a bug security.ts's own checks should already have prevented, not a value this layer can make sense of.
- **`hostToVirtual` is canonical on both sides, and that is ONE fix for what was filed as four bugs (#21, #35, and two more found in review).** The defect is one sentence: `security.ts` decides containment by canonicalising both sides (`isWithinAnyDir`), and this function used to decide the label by comparing STRINGS against the entry as the operator wrote it. Every way of making those two rules disagree reached a client on an `ok` result:
  - a granted root that is itself a symlink (**#21**) -- `fs_glob` walks from the resolved root, so every hit failed the string compare;
  - an aliased ancestor (`/Users/runner -> /Users/admin`, found on #21 on an ordinary macOS host with no unusual configuration) -- a pattern reaching the same files by both names returned each file twice, once named and once as the placeholder;
  - an `allowed_dirs` entry containing `..` (**#35**) -- `fs_list` and `fs_glob` redacted EVERY path while `fs_read`, `fs_grep` and `fs_find` worked, because the first two build their paths with `path.join` (which collapses the `..`) and the others echo back the string they were handed;
  - `/tmp` vs `/private/tmp`, which nobody had reported and which is waiting on any macOS host;
  - a `..` **together with** a symlinked ancestor, which is why enumerating spellings is not sufficient on its own: `path.join` collapses the `..` without resolving the link, producing a string that is neither what the operator wrote nor what `canonicalizePath` returns. This one survived the first, narrower fix and is what forced the general one.
  
  So `hostToVirtual` runs two stages. **Stage 1** prefix-matches `LabelEntry.spellings` -- the deduped literal/lexical/canonical forms of the grant, which is every spelling this repository can itself produce -- costing no syscalls and answering nearly every real path. **Stage 2**, only when no spelling matched, resolves `dirname(hostPath)` with security.ts's own `canonicalizePath` and tests containment against `realHostDir`: the same question, against the same canonical form, that `isWithinAnyDir` asks. Stage 2 deliberately uses the resolved PARENT plus the path's own `basename`, never a canonicalisation of the whole path -- that is `validatePathNoFollowFinal`'s rule (C2), here for the same reason: resolving the last component would rename an in-scope symlink to its target, so `fs_list` would report a name that is not the name of the entry it just listed. Stage 1 sits in front of stage 2 for COST, not correctness; stage 2 alone would be correct and would pay a `canonicalizePath` per emitted path, up to 1000 of them for one `fs_glob`.
  - **Neither stage widens what can be named, and this is the property to preserve.** Stage 2 is strictly WEAKER than the check every caller already ran -- its test is "the resolved parent is inside the grant", while `validatePath` (which every call site runs first) resolves the whole path including the final component -- so anything arriving at the map has already passed a harder test. Stage 1 is not a widening either: `canonicalizePath` resolves prefix-first, so `canonicalizePath(spelling + rest)` is the same path for every spelling of one directory; they name exactly the same set of files, and a `rest` that escapes through an inner symlink escapes identically through each and is stopped identically.
  - **The alarm is as much the point as the paths.** `hostToVirtualOrRedact`'s placeholder is fsmcp's signal for "a path reached output from outside the grant", and all of the cases above made it fire on correct, contained calls -- which trains an operator and an agent to ignore it, the worst thing that can happen to a signal whose whole value is that it never fires spuriously (the same lesson issue #22 records for `redactLeakedHostPaths`). **Do not "fix" a future redaction by widening the map until the path becomes mappable.** The only reason it was right to silence it here is that the strings provably denote one directory and stage 2 asks security.ts's own question. If a path is unmappable because it really is somewhere else, the redaction is the correct output and the bug is upstream. `tests/label-mapping.test.js` asserts the alarm still fires -- for every grant spelling, against a real file one level outside, a prefix-sharing sibling, and `/etc/passwd` -- rather than leaving that to the argument.
  - **Recommended and deliberately NOT done: canonicalise (or refuse) an `allowed_dirs` entry at intake.** Every case above is downstream of accepting an entry in a spelling nobody normalised, and normalising once in `main.ts` is cheaper than making every consumer agree -- #35 says as much, and it is arguably the real fix. It was left alone because it is a change to four contracts rather than one line: `hostDir` must stay byte-exact for `virtualToHost` (an already-resolved string would pre-empt `canonicalizePath`'s kernel-style walk), the entry string is what the dropped-`_meta` report and the duplicate-label refusal quote back to an operator, and `narrowAllowedDirs`'s C1 intersection compares the entries the operator supplied. It wants its own issue and its own tests.
- **A `LabelEntry` carries three things about its one directory, and they are not interchangeable.** `hostDir` is the literal string the operator or relay wrote -- **only `virtualToHost` may read it**, because handing `security.ts` an already-resolved string would pre-empt the kernel-style walk that is the whole point of `canonicalizePath`. `realHostDir` is that directory as `canonicalizePath` resolves it, and is the grant's IDENTITY: it is what `isWithinAnyDir` compares against, so it is the only spelling that can answer "is this path under this grant" the same way the security check answers it. `spellings` is the deduped set of forms this repository can produce (literal, `path.resolve`-lexical, canonical) and is a fast path for outbound translation, never a definition of scope. `assignLabels` is the one place in vpath.ts that asks what a path resolves to, and it asks by calling security.ts's own `canonicalizePath` rather than growing a resolution rule of its own -- the bug being fixed was this file DISAGREEING with security.ts about which strings name the same directory, so the fix has to be to ask it, not to reimplement it. `realHostDir`/`spellings` are optional on the TYPE and always populated by `assignLabels`; a hand-built `LabelEntry` carries only `hostDir`, which is precisely what f6baa96 cost -- `escapeRegExp(undefined)` thrown from inside `redactLeakedHostPaths`, the one function whose job is to fail safe. `spellingsOf()` is the single reader of those fields and it filters rather than assumes.
- Labels: `label=/abs/path` in an `allowed_dirs` entry (CLI or `_meta`, stripped by `stripLabels()` before the bare host path ever reaches `narrowAllowedDirs`/`validatePath` -- an unstripped `"label=/x"` is not absolute and would otherwise resolve against fsmcp's own CWD) wins; otherwise `d<N>` by position in the call's *effective* (already narrowed) scope. `_meta.allowed_dirs` and `--allowed-dir` themselves are unchanged: still plain host-path strings, still operator/relay-side.  **A duplicate label refuses the whole call, fail closed** (`assignLabels`, vpath.ts): `virtualToHost` resolves a label with `Array.prototype.find`, which silently returns the first match, so two directories sharing a label would not error on their own -- it would quietly make the second unaddressable and make `fs_glob`/`fs_find`/`fs_grep` report the identical virtual path for two different files, with `fs_read` of that path always landing on the first-registered directory. Reachable from two explicit `label=`s, or from an explicit `label=` colliding with another entry's auto-assigned `d<N>` (`--allowed-dir d1=/x --allowed-dir /y --allowed-dir /z`: `/y` is position 1, so it auto-assigns `d1`, colliding with `/x`'s explicit one -- a shape no operator would predict from their own flags in order). This codebase already refuses this SHAPE of ambiguity elsewhere rather than picking a winner (`fs_edit` on a non-unique `old_string`, `validatePath` on an empty scope), so `assignLabels` returns an `MCPCallResult` refusal instead of `LabelEntry[]` when it detects one. **That refusal names only the LABEL to the client; the two colliding directories go to stderr, for the operator** -- this file used to record the opposite ("naming both colliding directories -- safe, because both are always either a CLI directory or an already-narrowed `_meta` entry the caller itself supplied"), and that argument holds for the standalone CLI case and fails for the deployment this server exists for, where `--allowed-dir` is not passed at all and the whole scope arrives through `_meta` that **relay** populates from an operator's stored context. In that shape the colliding directories are the operator's host paths and the reader is the one party issue #7 exists to keep them from. The label alone is also the more useful half for each reader: a client cannot fix the configuration, and an operator needs both paths and has stderr. `main.ts`'s dropped-entry report (above) follows the same split, for the same reasons. `main.ts` returns that refusal directly, before `registry.call` ever runs, so every tool fails closed under a colliding configuration, not just an `fs_read` of the ambiguous address. The SAME directory landing on the SAME label twice (a literal duplicate `--allowed-dir`) is redundant, not ambiguous, and is not refused.
- **Scope refusals carry `_meta.scope_violation: true`.** `checkPath()`/`checkPathNoFollowFinal()` (security.ts) wrap `validatePath`/`validatePathNoFollowFinal` and return the ready-made `MCPCallResult` a tool handler should return directly -- `scopeViolationResult()` (types.ts) when the refusal is "outside your scope" (including the empty-scope case), plain `errorResult()` for everything else (bad regex, file not found, malformed path). Relay's audit reads this off a `tool_error` result as a field on that outcome, not a distinct outcome of its own -- it's what lets an operator's audit log tell "the sandbox held" apart from "the tool broke."
- **security.ts** validates paths via `validatePath()` -- resolves symlinks, checks prefix against allowed dirs. Empty allowed dirs = refuse everything (fail closed, not "no restrictions"); an operator who wants unrestricted access passes `--allowed-dir /` explicitly. NUL bytes and paths over `PATH_MAX` are refused up front (`basicPathError`), so they're clean refusals rather than an exception thrown three stack frames into `fs.lstatSync`.
- **Path resolution is component-by-component, not `realpath`-or-lexical.** `canonicalizePath()` walks from the root, follows every symlink in the part that exists, and carries only the not-yet-existing tail lexically. `fs.realpathSync` is all-or-nothing and throws for a path whose last component does not exist -- the ordinary case for `fs_write` -- and the old lexical fallback left symlink components in the string, so a symlink inside an allowed dir pointing outside it let a *new* file be written outside the sandbox. Two things the obvious "realpath the parent" shortcut still gets wrong: `..` must be applied to the resolved path, never collapsed lexically first (`<allowed>/sub/link/../../x` reads as `<allowed>/x` but lands outside -- and `fs.realpathSync` itself normalises `..` lexically, so this leaked *existing* files too), and a **dangling** symlink must be followed via `lstat`/`readlink` rather than treated as absent, because a write through it still creates the file at its target. **A `readlink` that FAILS returns `null` ("no canonical form I can determine"), the same as a symlink cycle, rather than throwing** (issue #36): `lstat` succeeding and `readlink` failing is an ordinary pair -- readdir permission on the parent is enough for the first and not for the second -- and it used to escape as an exception from three frames inside `validatePath`, in the middle of a tool's result loop. Measured as `EACCES ... readlink` surfacing as `fs_glob`'s `glob error:` branch. `null` is the fail-closed direction: every caller treats an unresolvable path as outside the grant, and an unreadable link is not evidence of containment. Do not rewrite this function; extend around it.
- **`validatePathNoFollowFinal()` (C2)** exists for `fs_delete` alone: it canonicalizes `dirname(path)` as usual but re-joins `basename(path)` un-followed, so deleting `<root>/link-out` (a symlink pointing at, say, `/etc`) refuses or succeeds based on the *link* being in scope, never on where it points. `fs_delete` then uses `lstat`/`unlink` on that exact path -- never `stat`, or the same follow happens one line later.
- **A path that resolves to a grant root is not a valid target for any tool that writes, creates or replaces something at it (issue #24).** One rule, two halves, living next to each other in `security.ts` and worded identically (`refusing to <action> an allowed_dir root: <path>`): `refuseAllowedDirRootWrite()` for the write side (`fs_write` "write to", `fs_edit` "edit", `fs_mkdir` "create", `fs_move`'s DESTINATION "move onto") and `refuseAllowedDirRoot()` for the remove side (`fs_delete` "delete", `fs_move`'s `overwrite` branch "overwrite"). Both are called through their `vpath.ts` wrappers (`refuseAllowedDirRootWriteV`/`refuseAllowedDirRootV`) so the refusal names the label, and both ask `resolvesToAllowedDirRoot()`, which compares CANONICALIZED paths -- `/d0`, `/d0/`, `/d0/.`, `/d0/notes/..` and an in-scope symlink pointing back at the root are one case, not five, and none of them is a string comparison against the label. `checkPath()` cannot make this call itself: a root is *inside itself*, so containment passes, correctly. What fails is everything downstream that derives a **sibling** of the target and, for a root, lands it one level up -- `writeFileAtomic`'s `path.dirname(filePath) + "/.<basename>.fsmcp-tmp-<random>"` temp file, `fs_write`'s own `fs.mkdirSync(path.dirname(resolvedPath), { recursive: true })`, and `fs_mkdir`'s `fs.mkdirSync(root, { recursive: true })` creating every missing ancestor of the root. Measured on the broken build: `fs_write { file_path: "/d0", content: <5MB> }` left 5,000,000 bytes of caller-chosen content in the grant's PARENT, with only the closing `rename` failing (`EISDIR`) after the bytes were already on disk outside the grant; with the parent chmod'd `0555` the failure moves to the `open` (`EACCES`), which is what proves the creation was aimed there rather than merely that the call failed. "The temp file is unlinked in `writeFileAtomic`'s `catch`" is not a defence -- cleanup is best-effort, does not run if the process is killed, and the file's size is caller-chosen up to `MAX_WRITE_BYTES` with a caller-influenced name, in what on a real machine is `~/Documents` or `~`. **The write half returns `scopeViolationResult()`, the remove half a plain `errorResult()`, and that asymmetry is deliberate**: servicing a root-addressed write really would have put bytes outside `allowed_dirs` (the sandbox held -- and before this fix `relay audit` showed only a bare `tool_error` carrying someone else's errno, so an operator reading the log had no way to see that a file had been created outside the granted directory), whereas refusing to *delete* the root removes only something inside the grant and is "the sandbox must survive its occupant", not "you addressed something out of scope" -- and `_meta.scope_violation` must mean only the latter. `fs_mkdir` refuses the resolved root whether or not it currently exists, rather than only when it would create something: an existence-conditional rule would be a second, weaker copy of the same rule decided by a race-able `stat`, and "your grant root already exists" was never a useful answer. **The caller-side refusal is the whole fix today.** `writeFileAtomic` asserting that `path.dirname(filePath)` is in scope is worth having as defence in depth and is deliberately not in this change (that file is being rewritten elsewhere); until it lands, these call sites are the only thing between a root-addressed write and the parent directory, so do not remove one without adding that assert first.
- **Recursive directory creation is bounded at the grant root, and a grant root that does not exist is refused rather than manufactured (issue #33).** `security.ts`'s `refuseMissingAllowedDirRoot()`, called by `fs_write` ("write") and `fs_mkdir` ("create") immediately after the #24 root check and before any syscall. This is #24's family one step wider: #24 closed the grant root ADDRESSED AS THE TARGET, and that refusal never fires for an ordinary, entirely legitimate path INSIDE the grant. `fs.mkdirSync(..., { recursive: true })` walks up until it finds a directory that exists and has no idea where the grant is -- when the grant root is missing too, the root is just another component on the way. Measured on the build with #24's fix in it: a grant at `<R>/level1/level2/level3/grant` with only `<R>` on disk, one `fs_write { file_path: "/d0/sub/file.txt" }`, and `level1`, `level2`, `level3` created OUTSIDE the boundary, reported as `Wrote 31 bytes`; `fs_mkdir { path: "/d0/sub" }` did the same and answered `Created directory: /d0/sub`. **The grant root existing IS the bound** -- that is why an existence precondition is the whole fix and a per-component mkdir walk (considered, not written) buys nothing: `checkPath()` has already established the canonicalized target is at or under a grant root, so every directory `recursive: true` could create is a strict descendant of that root, provided the root is there for the walk to stop at. Creating intermediate directories inside the grant is `fs_write`/`fs_mkdir`'s documented job and is untouched. **Refusing beats creating the root and stopping there**: the root cannot be created without creating its missing parents, which are outside the grant by definition, so the weaker alternative only helps when exactly one component is missing -- and a grant that does not describe anything on the host is a mistake that wants to be visible. A typo (`~/Documnets/project`) leaves the agent working productively where nobody will ever look; an unmounted volume is worse, because granting `/Volumes/Work/project` with the drive unplugged creates that path on the BOOT DISK, which then shadows the mount point, so macOS mounts the real volume as `/Volumes/Work 1` when it appears -- two similar names, the agent's data in the wrong one, and no error anywhere. `isWithinAnyDir()` already treats a granted directory that will not resolve as a real condition and skips it rather than letting it widen the scope; this is the same condition by a different route, given the same answer instead of the opposite one. **A plain `errorResult()`, deliberately NOT `scopeViolationResult()`**: the client addressed something squarely inside its own scope, and `_meta.scope_violation` has to keep meaning "the client addressed something OUTSIDE its scope" or an operator reading `relay audit` cannot tell a containment event from a mistyped grant. The cost is that relay currently renders this as a generic `tool_error`; the right fix is a distinct operator-facing signal in relay ("your grant points at nothing"), recommended to relay and deliberately not built by borrowing this flag. The message names the GRANT and says the retry is pointless -- an agent told "no such file or directory" for `/d0/sub/file.txt` concludes it typed the path wrong and retries, possibly forever, since nothing it can do client-side will make the operator's grant exist. It is wrapped in `translateResult(result, ctx.allowedDirs, ctx.labels)` at the call site rather than through a `...V` wrapper in `vpath.ts`, because the path embedded in it is the granted directory, not the target the `...V` wrappers translate; an untranslated grant path in an error result trips `redactLeakedHostPaths()` and the caller gets the internal-error backstop instead of the explanation. A grant that resolves to a FILE, or to a dangling symlink, is the same operator error and gets the same refusal (`fs.statSync`, not `lstatSync`, so a grant that is a symlink to a real directory keeps working). With NESTED grants, one usable root anywhere in the containing set is enough -- the walk stops at it, and everything created is still inside something the operator granted -- so `containingAllowedDirs()` returns all of them, most specific first, and only an entirely missing set is refused.
- **Tool output that is a path is re-validated.** `fs_glob`, `fs_find` and `fs_grep` all filter every hit through `validatePath` rather than trusting descendants of a validated directory: whatever walks the tree chooses what gets reported, so a symlink inside an allowed directory that points outside it can come back as an in-scope-looking path. `fs_list` does not recurse, so it has no such gap: every entry it reports is `path.join(validatedDir, entry.name)` for a name `readdir` produced, which cannot contain a separator or `..`.
- **`fs_glob` walks from a RESOLVED root (issue #21), and that is the only thing about the walk that changed.** `globSync`'s default `follow: false` does not merely decline to follow links inside the tree -- it will not walk THROUGH a `cwd` that is itself a symlink, so a recursive `**` pattern against a grant reached through a link (`/tmp` on macOS, a relocated home, an external volume, a cloud-storage alias -- none of which an operator has to have thought about) returned **an empty success**: the client was told the folder was empty and `relay audit` recorded `ok`, which is the one shape this stack's runbook says must never happen. A pattern whose first component is a literal (`sub/*.txt`) sidesteps the `**` walk and worked, which made the failure look intermittent rather than total; `fs_find`, `fs_grep` and `fs_list` were unaffected. The fix is `canonicalizePath(dir)` (security.ts, the only resolver here, and the same one `isWithinAnyDir` uses to decide what "inside this grant" means) as the `cwd` handed to `globSync`. **`follow: true` is not the fix and was measured: it does not resolve a symlinked `cwd` at all, and it would additionally make glob follow every link INSIDE the tree -- precisely the traversal the per-hit re-validation above exists to catch.** Resolving the root changes where the walk starts and nothing about what it is willing to walk through: every symlink under the root is still un-followed and every hit still goes through the real, unmodified `validatePath` (measured against the fix: with `escape_file.txt -> <outside>/secret.txt` inside a symlinked root, `**/*.txt` genuinely returns that link from `globSync` and `validatePath` genuinely drops it). A root that will not resolve at all is skipped -- what `isWithinAnyDir` does with the same case, for the same reason -- and if that leaves nothing to search the result is an ERROR about the directory, never an empty success. Note the pairing: **canonicalising the walk is necessary and, on its own, actively worse.** Applied alone against `main`, every hit comes back spelled with the resolved root, matches no label's `hostDir`, and the caller gets a page of `[fsmcp: path outside the granted directories -- redacted]` instead of a page of filenames -- an empty answer traded for a false alarm. The outbound half (`hostToVirtual` matching both spellings, above) is not optional, and `tests/symlinked-root.test.js` pins both halves independently so neither can be reverted quietly.
- **`fs_glob`'s `pattern` is validated before it reaches the filesystem, a pattern may not name a LOCATION (issue #25), and the WALK is confined to the grant whether the pattern is recognised or not (issue #36).** `pattern` was the one path-shaped input in this server that never went through `decodeInboundPath`/`checkPathV`, and `globSync` ignores `cwd` completely for an absolute pattern -- so `pattern` was a host-path traversal primitive that the validated `path` argument did not bound. The per-hit `validatePath` filter held (no name and no byte from outside the grant was ever emitted), which is precisely what made this hard to see: **what escaped was not data, it was answers.** `<grant>/**` returned hits, one character wrong returned an empty string, and `?`/`*`/`[a-r]` turn that difference into a character-by-character search of the host's layout -- the capability issue #7 exists to remove, handed back by the only tool that takes a pattern. **Output filtering cannot close an oracle whose signal IS the empty output**, which is why this is a check on the input and not a better filter on the results. Two more consequences fell out of the same root: naming somewhere out of scope was an empty SUCCESS (`{"pattern":"/etc/…"}` -> `ok`, `""`), making fs_glob the only tool here where addressing something outside the grant was not a refusal; and the walk was unbounded, so one call could walk `/System/Library` while every OTHER client of the same shared, synchronous child waited. The rule all three collapse to: **a pattern is a pattern, not an address.** The address is the `path` argument, which is already decoded from the virtual space and already validated; a pattern may only describe names UNDERNEATH it. So, before a single syscall: an absolute pattern is refused, a `..` component is refused, and both are `scopeViolationResult` (same classification `decodeInboundPath` gives "you did not name anything in fsmcp's address space", same reason -- a caller that cannot spell an address inside its grant is naming something outside it), with **no echo of the pattern**, because a refusal that varies with its input is the same oracle one level up. A NUL in a pattern is a plain `errorResult` -- malformed input, not a scope violation, matching `basicPathError`'s treatment of the same byte in a path. **Issue #36 is the sequel and the sub-bullets below are written from it: the rule survived intact and both of #25's checks were replaced.** They were regexes over the raw pattern text; `[.][.]/*` and `\.\./*` parse to the same components as `../*`, neither regex saw a `..` in either, and `[.][.]/[.][.]/[.][.]/**/*` walked out of the grant for 44.08s against a 30s budget while blocking a different enrolment's `fs_read` for 42.17s. Nothing escaped -- the per-hit filter held again -- so this was traversal and denial of service, not disclosure. What replaced them is one check derived from glob's own parser and one structural bound inside glob's walk, and the reasoning that left the hole open is corrected below rather than deleted.
  - **Both checks used to be conservative regexes over the RAW pattern text, and issue #36 is what that cost. They are now glob's own parser's answer, and the containment does not depend on them at all.** The regexes were argued for here as follows, and the argument is kept because the way it failed is the useful part: brace alternatives really can hide either shape (measured, `{/etc,sub}` with a wildcard below it returns `/etc/hosts` and `{sub,..}` returns the search directory's parent) and `path.isAbsolute` sees neither, so `..` was matched as a TOKEN at any component boundary and a `/` after `{`/`,` was treated as an absolute alternative; the exact test would mean importing `minimatch` or hand-writing an expander that has to agree with someone else's parser forever, and "a containment rule that tracks another package's grammar is a hole waiting for a version bump."

    **That last sentence was right and the conclusion drawn from it was wrong.** A regex over the raw text does not avoid tracking someone else's grammar -- it tracks it badly, from the outside, without saying so. `glob` walks the component list `minimatch` produces, not the text, and `[.][.]/*`, `\.\./*` and `../*` all produce the identical components `['..', /…/]`. Measured on the merged build: `../*` refused; `[.][.]/*` and `\.\./*` not refused. **The specific paragraph that talked this hole into existence was this one:**

    > it deliberately does NOT try to catch a `..` produced by a magic component, because Node's `readdir` never reports `.` or `..` as entries, so only a literal `..` component can climb.

    The premise is true, the conclusion does not follow, and the gap between them is a layer. **The premise is about `readdir`; the conclusion is about minimatch's parser**, which runs first. A component that is still magic when the walker sees it is indeed only ever matched against directory entries, and `readdir` indeed never offers `.` or `..` -- that part is sound and is why a RegExp component needs no check. But `[.][.]` does not stay magic: minimatch normalises a character class with one static member to that member, so it becomes the *string* `'..'` before any entry is matched, and a string component is consumed by path ARITHMETIC (`Path.resolve(p)` in glob's Processor), which climbs. The refusal was checking a spelling; the walker was reading a parse.

    So the check now asks the parser: `new Glob(pattern, …).patterns` is the component list the walk will use -- one entry per brace alternative, each a list of components -- and it is built with no syscalls, so this still runs before anything reaches the disk. A `'..'` string anywhere in it is refused; an alternative whose `root()`/`isAbsolute()` says it starts at the filesystem root is refused, which covers `{/etc,sub}/*` without a second rule. **This is not a third regex**: it is not a statement ABOUT glob's grammar that has to be kept in step with it, it is glob's own answer, so a version bump changes the answer rather than invalidating the rule. `glob` remains the only runtime dependency -- `Glob` is one of its documented exports and `minimatch` is not imported.
  - **A `..` that survives the parse is refused even when it would have stayed inside the grant; one glob has already removed is not. That line moved in #36, and this is the old reasoning and why it changed.** It used to read: "a pattern with a wildcard before the `..` does not resolve to one path, so there is nothing to hand the containment check", and resolving patterns "where possible" would leave a boundary a caller could probe. That was true of a regex, which cannot resolve anything. It is not true of the parser, which is what decides now -- minimatch collapses `<component>/..` itself, before the walk, so `sub/../top.txt` arrives as the components `['top.txt']` and `*/../top.txt` as a single magic component. There is no `..` left, no path arithmetic happens, and refusing them would be refusing patterns that provably cannot climb. Where the `..` survives (`**/../x`, `sub/../../x`, and -- because minimatch's collapse runs on the raw string parts, before a one-member character class is normalised -- `sub/[.][.]/top.txt`) it is refused exactly as before. **The boundary #25 worried about is real, and it is not probeable**: it is decided by the pattern text alone and never by what is on disk, so `sub/../top.txt` and `nosuchdir/../top.txt` walk the same thing and give the same answer. The `sub/../top.txt` vs `sub/[.][.]/top.txt` split is minimatch's, reported rather than smoothed over: smoothing it would mean predicting the parser again, and it costs nothing, since both answers are the same on every host and the refusal is the conservative half. Every directory in scope is still addressable by naming it with `path`.
  - **Containment is the WALK's property now, not the pattern check's, and the two are deliberately different mechanisms.** `walkGuard` (glob.ts) is passed as glob's `ignore` hook: `ignored` runs for every candidate match, `childrenIgnored` before descending into any directory, and both refuse anything not inside `ctx.allowedDirs` -- the same question the per-hit `validatePath` filter already asked, moved from "drop it from the results" to "do not go there". `childrenIgnored` prunes a subtree outright, so a walk pointed out of the grant stops at its first candidate instead of enumerating a tree and discarding it. **Measured with the pattern check deliberately disabled, so the hook is the only thing left**: `[.][.]/**/*`, `[.][.]/[.][.]/[.][.]/**/*` and `[.][.]/*` all returned in 46-48ms (process spawn) against 723-818ms on `main` for the same fixture, and all three came back as scope violations. **The hook alone is not sufficient, which is why both exist.** With it as the only check, `[.][.]/grant/*` returned `/d0/top.txt` and `[.][.]/grXnt/*` returned `No matches found.` -- #25's host-path oracle, through the spelling #25 missed. A pattern that climbs out and comes straight back IN never offers the walk a candidate outside the grant, so the walk has nothing to object to; only something that reads the pattern can. That is the division: **the parser check answers "may this pattern be walked at all", the hook answers "may this directory be entered", and the per-hit `validatePath` filter answers "may this hit be shown".** None of the three was removed as redundant -- "now redundant" is the argument that left the `[.][.]` hole open.
  - **The cost of the hook on an ordinary in-grant walk is a string compare, not a `canonicalizePath`.** A resolve per candidate would put an lstat-per-component on the hot path of every `**` in the deployment, so the test is layered: a candidate lexically under one of the (already `canonicalizePath`'d) search roots is in scope for one prefix compare and no syscall; a SYMLINK gets the real `validatePath`, because its target is a different question; a candidate under none of the roots gets `validatePath` too, since nested or differently-spelled grants are ordinary, and only a "no" from that counts as the walk having escaped. Measured, 4,400 directories / 24,000 files, `**/*.txt`, best-of-9 per run: `main` 589/589/588ms, branch 598/605/606ms -- about **2-3%**, ~15ms on a 590ms walk. **`escaped` is set only in that last branch, and that matters**: an in-grant symlink pointing out of the grant is an ordinary thing to find, it is dropped as it always was, and it must not turn a correct `**/*` into a scope violation. The flag means "the WALK left the scope", not "something out of scope was noticed" -- pinned by a test.
  - **Where "out of scope" versus "matched nothing" is decided, now that the walk is pruned rather than pattern-inspected.** In the parser check, before any syscall -- not in the walk. The walk structurally cannot make that call: a pruned candidate and an absent one are the same empty answer, which is #25's defect restated. The walk-side refusal (`WALK_ESCAPED_REFUSAL`) exists anyway as the backstop for a climb the parser did not recognise, and is unreachable as the code stands -- deliberately kept, because "unreachable" here is a claim about someone else's parser, which is exactly the claim #36 falsified.
  - **The walk is bounded by the shared `grepBudgetMs()`, enforced through the same `ignore` hook -- and the budget now covers the work AFTER the walk, which is where #36 found it leaking.** The 1000-result cap bounds the OUTPUT, not the traversal: a pattern that matches nothing walks everything and returns an empty list having done all the work. Checking the clock between yielded results does not work either -- a pattern that matches nothing yields nothing to check between -- so the deadline rides on `ignored`/`childrenIgnored`, which glob calls as it descends whether or not anything matches. Measured: a globstar over `/System/Library` returns at the budget, to the millisecond. **What that bounded was `globSync` and nothing else.** The per-hit `validatePath` loop underneath it is a `canonicalizePath` per hit -- an lstat and possibly a readlink per component -- over a list with no bound of its own, so a walk cut off at 30s spent a further 14s validating what it had already collected: **44.08s against a 30s budget, measured**, head-of-line blocking an unrelated enrolment's `fs_read` for 42.17s. It then did not even reach the graceful cut-short path, because `canonicalizePath` let an `EACCES` from `readlink` escape as a THROW and the call ended in `glob error:` instead. Both halves are fixed: the guard exposes `outOfBudget()` and the hit loop breaks on it, and `canonicalizePath` returns `null` for an unreadable link (see the path-resolution bullet above). The mtime `statSync` loop is deliberately not separately budgeted -- one syscall per match, over a list the budgeted loop above it has already bounded. A cut-short walk **says so** and, when it found nothing at all, says only that -- an incomplete answer that reads as a complete one is the same failure as #21's empty success. `fs_glob` reuses fs_grep's and fs_find's budget rather than inventing a third: the hazard is "one synchronous process serves every caller", a property of the server, not of a tool.
  - **#21 and #25 interact and were fixed together.** #21 teaches the outbound map the RESOLVED spelling of a grant; on its own that widens #25's oracle by one spelling, because an absolute pattern naming the real target of a symlinked grant began mapping to real `/d0/...` paths where it previously came back redacted. #25's refusal closes both spellings before the walk -- and it still does under #36, because `root()`/`isAbsolute()` on the parsed pattern is the same verdict for both spellings that `path.isAbsolute` gave for one. Pinned by a test in `tests/glob-pattern-scope.test.js` that grants a symlinked root and refuses an absolute pattern in either form.
- **These tools' output is one result per line, and that sentence is now enforced in all four of them rather than assumed in one (issues #31, #37).** `fs_list`'s record is `type\tsize\tmtime\tpath`; `fs_glob` and `fs_find` are a path per line and nothing else; `fs_grep` is a path per line, `path:count`, or `path:line:content`. The shared machinery is `src/resultFormat.ts` -- `escapePathField()`, `pathFieldEscapingRules()` (the sentence each description carries) and `RESULT_TRAILER_RULE`. It lives there rather than in `list.ts` because that is precisely how #37 happened: #31 wrote the scheme down inside the one tool it was first needed in, and the other three did not adopt it.
  - **The path field is backslash-escaped** (issues #31, #37): a literal backslash as `\\`, and the three characters that carry structure in a line-and-tab format as `\n`, `\r`, `\t`. Nothing else is escaped by default, and no field other than the path is (`fs_list`'s type, size and mtime are all generated). A filename containing a newline is legal on every POSIX filesystem including APFS -- and creatable through fsMCP's own `fs_write`/`fs_move` -- and was emitted raw, so one result became two lines: a phantom record, and a real record truncated at the newline. Nothing errored; the format silently stopped being the format, in the caller's parser rather than here. **The backslash pass runs first and unconditionally**, which is the only reason the scheme is reversible: without it a file literally named `a\nb` and a file whose name contains a real newline emit identical bytes, and a caller unescaping would conjure a newline into a name that never had one. That is also the one behaviour change for ordinary paths -- a backslash in a path now comes out doubled. **Every one of the four tool descriptions states the rules, including the left-to-right decoding order**, because an escaping scheme a caller is not told about replaces one silent parsing failure with a different one. Escaping was chosen over skipping such an entry (which would make a real, reachable file invisible to the tools whose job is to say what is there, while every other tool still operated on it happily) and over emitting structured content (the clean answer, and a much larger change worth making only if these tools are reworked as a group).
  - **`fs_grep` escapes `:` as well, and NEVER escapes the matched content -- the one place this scheme is not a straight copy.** The colon is `fs_grep`'s field separator, so a path containing one broke `path:line:content` and `path:count` independently of newlines and always had (`/d0/a:b.txt:3:hit` reads as a file called `/d0/a` on line `b.txt`). It is escaped in EVERY output mode, `files_with_matches` included, so one unescaper works on every `fs_grep` reply rather than a caller having to remember which mode it asked for; the promise is exact -- the path field never contains an unescaped colon, so the first unescaped colon ends it. **The CONTENT field is the file's own bytes and is not escaped, translated, or altered in any way.** That is PR #10's rule (a whole-result rewrite once silently corrupted a file whose bytes contained the sandbox path, caught by a write-then-read byte round trip) and escaping content would be the same mistake in new clothes: `fs_grep` would report a line that `fs_read` disagrees with, and a caller would have no way to know which to believe. **Residual, stated in the tool description rather than left to be discovered:** with `context` set, the ripgrep backend reproduces plain rg's own separators and a CONTEXT line uses `-` where a match line uses `:`. `-` is deliberately NOT escaped -- hyphens are ubiquitous in real paths, so escaping them would put a backslash in nearly every line of every context reply to make a rare case parseable -- so a path containing `-` cannot be told from a context separator, and a caller that must parse paths mechanically should use `files_with_matches`, whose lines are one escaped path each.
  - **Results end at the first blank line; the `(showing X of Y ...)` trailer follows it.** Same promise, second half of #37: `fs_list`/`fs_glob`/`fs_find`/`fs_grep` all append a cap note or an `[fsmcp: ...]` advisory, and a caller splitting the payload on `\n` was reading those as two more results. **Documented rather than removed, deliberately** -- issue #11's rule is that a bounded answer says so BOTH structurally (`_meta.truncated`) and inline for a human, so dropping the inline half to make the payload uniform would trade a stated parse rule for a silently short answer. What makes it parseable is the blank line these tools already emitted before it: no result line is ever empty (`fs_list` always has four fields, `fs_glob`/`fs_find` always a non-empty path, `fs_grep` always a path and a separator), so the first empty line is an unambiguous end-of-results marker. That was already true; it was just never written down. `RESULT_TRAILER_RULE` is the sentence, in all four descriptions.
  - **`fs_find`'s ripgrep backend passes `--null`, and that is #37's defect pointing INWARD** (found while fixing it, fixed with it). `listFilesRg` split `rg --files` output on `\n`, and `rg --files` writes one path per line -- so a file named `we<LF>ird.txt` arrived as the two strings `./we` and `ird.txt`, both were dropped by the per-hit `validatePath` re-check, and the file was simply **invisible to `fs_find` on every host with ripgrep installed**, while the Node fallback (which builds paths from `readdir` entries) listed it fine. Measured against ripgrep 15.2.0. Escaping the path on the way out would have been a promise about a name `fs_find` never had. `--null` terminates each path with the one byte a POSIX filename cannot contain, so the split is exact rather than probable; the trailing empty string is dropped by the `filter(Boolean)` that was already there. `fs_grep`'s rg backend needed nothing here -- it has passed `--json` since issue #7, which gives the same split structurally -- and `fs_glob` gets its hits from the `glob` package as an array.
  - **A symlink's size is reported as `0`** (issue #28). `listOneDir` uses `lstat`, which is correct -- it must not follow the link -- and printed `st.size`, which **for a symlink is the byte length of the target path string**. The size column was therefore an exact measurement of a path the client is not allowed to know exists, on the one entry type where every other surface refuses to say anything at all (`fs_read` of that same link is "outside allowed directories"). A few bits on its own, worth more against a guessable prefix: a `latest -> /Volumes/Backup/2026-08-26-nightly` shape is ordinary in a real tree and its length confirms or eliminates a candidate host path in one call, and `fs_move` lets a client rename links freely, so links are cheap to enumerate. Zero costs nothing, because a link's own size is not the size of anything a caller can read. The doc comment above `listOneDir` asserted the containment property this only now has -- "disclosed only as a name and a type", while the size column was disclosing the target's exact length -- and has been corrected to describe the code.
- **fs_grep** shells out to `rg` if available, falls back to recursive readdir + RegExp; both paths are bounded by `grepBudgetMs()` and both re-validate every path before it reaches the caller. The `rg` path always passes `--json` (never `-l`/`-c`/`-n`), parsed by `formatRgJson()`: issue #7 needed something to reliably split "this substring is the path" from "this substring is the file's own content" in order to translate only the former, and the old plain-text parsing (`path:line:content`, regex-anchored on the numeric line number because content can itself contain colons) was already flagged as fragile for an unusual filename -- building a rewrite step on that fragility would have made it load-bearing in a new way. `--json` gives the split structurally (`data.path.text` vs `data.lines.text`) instead. `-c`/count cannot be combined with `--json` (verified against a real ripgrep: it silently reverts to `-c`'s own plain output), so count is derived from each file's `end` event (`stats.matched_lines`) instead. The Node fallback (`grepFallback`) builds its own output strings from paths it already controls, so it needs no JSON round-trip -- but it does need `hostToVirtualOrRedact` on every path it emits (an optional `labels` parameter, threaded from `ctx.labels` at the real call site and left `undefined` for the ReDoS-budget unit tests that have no concept of labels at all). An earlier version of this reasoned that `ToolRegistry.call`'s generic outbound pass (`redactLeakedHostPaths`) would cover it instead; that pass is scoped to `isError` results only (see "Outbound translation is deliberate" above), and an ordinary successful search is never an error result, so the sandbox's real absolute path came back unmodified in every output mode on any host without ripgrep on PATH -- fixed by translating each path at grepFallback's own three emission sites, the same as everywhere else in this file. Matched line TEXT in content mode (`lines[idx]`) is never touched, for the same reason `formatRgJson`'s `lines.text` and `fs_read`'s own bytes are not. **`grepWithRg`'s catch-all error branch used to return `rg`'s stderr verbatim (`grep error: ${detail}`) -- the one call site in this codebase that translated no path at all -- on the reasoning that ripgrep's free-text errors carry no `.path`-shaped field to translate and that `redactLeakedHostPaths`'s `isError`-scoped backstop would catch a granted directory if `rg` printed one. It did not, and issue #22 is what that cost.** The backstop's path-boundary lookahead was `(?=[/\n]|$)`, and `rg` -- like essentially every Unix tool -- writes `<path>: <reason>`. A colon was not in that class, so a message naming a granted **root** went to the client byte for byte (the host's account name, the layout above the grant, the real absolute path) while the byte-identical message naming anything *inside* that root, followed by `/`, was caught. Two ordinary operator conditions reached it, both reproduced live through relay: a granted root renamed out from under a call (`rg: <root>: IO error for operation on <root>: No such file or directory (os error 2)`) and a granted root the server process cannot read (mode 000, or a macOS TCC-protected folder -- `rg: <root>: Permission denied (os error 13)`, on a default-scope search with no `path` argument at all). **The earlier claim in this paragraph -- that a live check with a stub `rg` had confirmed the backstop caught this ("came back redacted, not leaked") -- was wrong, and wrong in an instructive way.** For that check to have passed, the stub's stderr can only have put a newline or a `/` after the root, since those are the sole shapes the old lookahead accepted; what it demonstrated was that the backstop catches the message the stub happened to write, not the message ripgrep actually writes. A stand-in that reproduces the mechanism but not the bytes is not a test of the bytes. That is why this paragraph asked for re-verification against a real failing `rg`, and why the fix was verified that way -- every `rg` stderr string quoted here was measured against ripgrep 15.2.0 on the host, not written from memory.

  The fix is the same per-call-site pattern as everywhere else, not a widened backstop. The paths that can appear in `rg`'s stderr are not arbitrary: they are the search directories fsmcp itself just put on the argv (or descendants of them, which are lexically prefixed by them -- the same property `describeError` relies on), so `translateResult(result, searchPaths, labels)` renames the known strings and leaves everything else, including the caller's own echoed pattern on a regex parse error, byte for byte. **No parser for ripgrep's prose was added, and none should be** -- that is exactly the fragility `--json` replaced for matches, and a wrong split there would not mis-format a result, it would emit a host path. Before falling back to `rg`'s words at all, the branch asks the *filesystem* what is wrong with the search paths it already knows (`unsearchableReason()`, `fs.statSync` + `fs.accessSync` with `R_OK`/`R_OK|X_OK`), which is how `fs_grep` now answers `directory not found: /d0/nodir` and `directory not readable: /d1` in the same words `fs_glob`/`fs_find`/`fs_list` use. That check also runs up front on an explicit `path` argument, before either backend, because both were wrong in their own way: the `rg` path produced the leak above, and the Node fallback's walker swallows its own `statSync` ENOENT and answered `No matches found.` -- a success result claiming something about a directory that does not exist. Which account to give when both could be true (an unreadable root *and* a pattern `rg` refuses to compile) is settled structurally, not by reading rg's text: `--json` emits a `summary` event once a search has actually run, and emits nothing on stdout when `rg` rejects its own arguments (measured: a missing or unreadable directory still summarises; `--type nosuchtype`, an unparseable `--glob`, and an uncompilable pattern do not), so a summary means fsmcp's filesystem diagnosis is the better answer and no summary means only `rg` knows. **The second half of issue #22 was that the backstop had become `fs_grep`'s routine error path** -- a mistyped directory answered "this is a bug in fsmcp, not a property of the request; please report it", for a typo. An alarm that fires in normal operation is not an alarm; `redactLeakedHostPaths` is back to being one. `rg` also exits 2 for *any* error it hit, including one it walked straight past, so a single mode-000 file anywhere under a granted tree used to turn a whole successful search into that generic refusal with its matches discarded; the matches are now returned with an explicit floor note (`grepFallback`'s own budget-truncation note is the same shape). That note rides on a SUCCESS result, which the backstop is `isError`-scoped and structurally cannot inspect, so it is built only from fsmcp's own words and `hostToVirtualOrRedact`'d paths -- nothing derived from `rg`'s output goes in it, ever. **Residue, stated rather than assumed:** a path in `rg`'s stderr that is under no granted directory at all (ripgrep naming its own `RIPGREP_CONFIG_PATH` file, say -- which exits 0 today, so it does not reach this branch, but is the shape to watch) has nothing to translate against and nothing for the backstop to match; and a granted root that is missing in a *default-scope* search is still dropped silently by the `existsSync` filter this tool shares with `fs_glob`/`fs_find`/`fs_list`, so that call still answers as if the scope were smaller. Treat any change to this branch as a reason to re-verify against a real failing `rg` -- produce the actual conditions, read the actual bytes.
- **fs_find** = `rg --files --no-follow --null` (Node walker fallback, which skips every symlink outright) + in-process fzf-style subsequence scoring (contiguity + word-boundary bonuses) over the resulting, re-validated file list. No new dependency -- `glob` stays the only runtime one. It shares `fs_grep`'s root cause for ripgrep failures and was fixed with it (issue #22): `listFilesRg`'s catch-all returned `{ files: [], truncated: false }` for anything that was not a timeout, so ripgrep's exit 2 -- which it uses for *any* error it hit, including one it walked past -- came back as `No matches found.`, a SUCCESS. Measured: one granted root at mode 000 made `fs_find` claim there was nothing matching in **any** root, silently discarding the real hits from the readable ones. The partial listing is now kept the same way the timeout's is, the failure is reported, and the caller diagnoses the roots itself (`unsearchableReason`) instead of repeating ripgrep's text -- `fs_find` has never shown `rg`'s stderr and does not start now, which is what kept this bug a *lost result* rather than a second copy of `fs_grep`'s leak. An explicit `path` is checked for readability, not just existence, before either backend runs, for the same reason: `existsSync` is true for a directory this process cannot open. `fs_find` and `fs_grep` are correct under a symlinked root (issue #21) **for a reason neither of them chose**: `rg` echoes back the unresolved directory string it was handed, and the Node fallbacks build their paths with `path.join` from that same string, so what they emit happens to be spelled the way `hostToVirtual` used to require. Since issues #21/#35 that is no longer load-bearing -- the outbound map recognises every spelling and falls back to a canonical containment test -- but it was never pinned before, so `tests/symlinked-root.test.js` pins both tools under a symlinked root as well as `fs_glob`, and `tests/label-mapping.test.js` pins all four tools across every grant spelling. If either ever starts emitting resolved paths (a new `rg` flag, an output-mode change, a fallback rewrite that realpaths), the mapping already handles it and the tests say so.
- **fs_edit** uses `split().join()` for literal matching (no regex special char issues), and **refuses both of that primitive's degenerate inputs up front, before the file is read** (issue #30). `content.split("")` splits into CHARACTERS, so an empty `old_string` counted `length - 1` phantom occurrences and `parts.join(new_string)` interleaved the replacement between every character of the file: `hello` was written back as `hXeXlXlXoX` and reported as `Replaced 5 occurrence(s)` on a success result, with relay's audit recording `ok`. The un-flagged path was the worse half -- `old_string found 5 times. Use replace_all or provide more context to make it unique` is a sensible sentence about a real string and a nonsense one about an empty one, and it names the flag that performs the damage as its own remedy, which is the shape this codebase already had to fix twice in `fs_move`. `old_string === new_string` is refused for the same "the operation has no meaning" reason rather than let through as a no-op: fs_edit rewrites through `writeFileAtomic`'s temp-file rename, so identical strings still replace the inode, break any hard link and bump mtime while the bytes stay what they were, and `Replaced N occurrence(s)` is a true sentence that reads as a change that did not happen -- a refusal is the answer that makes an agent look at its own strings, where a `0 changes` success would still be counted as a completed step by anything branching on `isError`. Neither trigger is contrived: both are what an agent produces when a search string came from a variable that resolved empty, or when two template variables resolved to the same value. An empty `new_string` is legitimate (deletion) and is untouched. `old_string` also carries `minLength: 1` in the published schema -- spelled inline rather than by extending `stringProp`, since it is the only length floor in the server -- so a caller that validates before sending sees the constraint without making the call that used to corrupt the file; the handler check is the enforcement, the schema keyword is the courtesy. and refuses a `file_path` that resolves to a grant root before it reads anything (issue #24). Nothing reached `writeFileAtomic` for a root here even before that check -- `fs.readFileSync` of a directory throws `EISDIR` and the handler answered "file not found" -- but that was an accident of ordering, dependent on a read failing first for an errno nothing here inspects, and "file not found" is the wrong answer for a path that exists and is the caller's own grant root. **It is also bounded on both sides now (issue #38), which it was not.** #19 bounded what crosses the stdio transport for `fs_write` only, so `fs_edit` -- the other tool that takes caller-supplied file content off the wire -- had no inbound bound at all: a 3 MB `new_string` landed on disk while the byte-identical `fs_write` refused at 1,048,576 (measured). That is not an outage (relay refuses an oversized REQUEST frame cleanly at `bridge.MaxMessageSize`; #19's outage was on stdout) -- it is the published limit being untrue for half the write surface, and `fs_edit` being the one mutating tool whose input nothing here bounded. `MAX_STRING_WIRE_BYTES` is `MAX_RESPONSE_BYTES`, out of the same constant because these are two spellings of one operation, and it applies to `old_string` AS WELL AS `new_string` -- equally caller-supplied, equally unbounded, and bounding only the half that reaches the disk would leave the message unbounded. Measured with `wireBytes` (`JSON.stringify` + `Buffer.byteLength`), never `.length`: 300,000 C0 control characters are 300,000 UTF-16 code units and 1,800,000 bytes on the wire. Separately, `fs_edit` read its target with a bare `fs.readFileSync` and NO size check, which in a single synchronous process is an unbounded allocation blocking every other caller -- the hazard `MAX_READ_BYTES` exists for, reached through a different door -- so `MAX_EDIT_READ_BYTES` (10 MiB, `fs_read`'s number) is checked from a `statSync` that now runs BEFORE the open and also supplies the mode `writeFileAtomic` needs. **The advice in both refusals is honest, which is the part that took the thought.** `fs_write`'s over-size message can suggest writing the file in pieces; `fs_edit` has no offset, append or windowed mode, so that sentence would be false here -- and a refusal that names a remedy which does not work is exactly how issue #23 destroyed files. So the string refusal says what does work (split the REPLACEMENT into several smaller edits, each anchored on surrounding text -- an edit is divisible without an offset because the file's own text is the anchor, including text a previous call just wrote), and the read refusal says the true and unwelcome thing: a file that large cannot be edited in place through fsMCP at all, only inspected with `fs_read`'s base64 windows.
- **The empty page is an ordinary answer, not a size failure.** #19's first version keyed its "this line does not fit the response budget" refusal on `formatted.length === 0`, which is also true for an `offset` past the last line (exactly what paging to the end looks like) and for `limit: 0`. Both came back as `line 5 of /d0/short.txt does not fit in fs_read's 1048576-byte response limit`, which is false about a three-line file and sends the caller to base64 windowing for a file it had already finished. Keyed on `lines.length === 0` now, and the size refusal is reached only when there really was a line and it really did not fit -- **which cannot happen at the shipped defaults at all**, since `MAX_LINE_LENGTH` (2000 chars) truncates a wide line long before `MAX_RESPONSE_BYTES` (1 MiB) could reject it. That branch is for a raised `--max-line-length` (issue #16), and `tests/read-empty-page.test.js` says so out loud rather than pinning a condition the defaults make unreachable.
- **Three size defaults, and they are not independent (issue #19, retuned).** `MAX_RESPONSE_BYTES` = **64 KiB** (one payload: fs_read's output, fs_write's/fs_edit's inbound strings), `MAX_SEARCH_RESULT_BYTES` = **16 KiB** (a LISTING: fs_glob/fs_find/fs_grep/fs_list, via `capLines`' default budget), `MAX_BASE64_FILE_BYTES` = **32 KiB** (whole-file base64). The binding constraint on all three is the CONTEXT WINDOW of the model on the other end, not relay's 10 MiB frame cap -- the original 1 MiB was chosen as "10x under relay" and that was the wrong question: 1 MiB of text is ~350K tokens, which crosses the wire perfectly and then destroys a 200K context on arrival. **The base64 ceiling must stay meaningfully below `floor(MAX_RESPONSE_BYTES * 3/4)`** (= 48 KiB here, since base64 inflates by 4/3) or it can never fire, and a limit a caller is told about but cannot reach is worse than none -- it sends them to the wrong remedy. That is exactly what happened when the response cap came down and the 256 KiB ceiling was left behind: 5.3x the cap, unreachable, still advertised. `MAX_RESULT_BYTES` (the backstop) is DERIVED as `MAX_RESPONSE_BYTES + 16 KiB` so it cannot drift below the payload budget it is supposed to backstop -- an alarm smaller than the thing it watches fires on ordinary results and teaches everyone to ignore it. `RESULT_NOTE_RESERVE` came down 4 KiB -> 1 KiB for the same reason: 4 KiB was 0.4% of a 1 MiB budget and would be 25% of a 16 KiB one. Nothing became unreachable at these numbers -- fs_read pages and windows, the search tools cap and report -- so the cost is calls, not answers. Issue #16 makes all of them flags.
- **Every result is bounded in WIRE BYTES, and the bound is a property of results, not of one tool (issue #19).** fsmcp used to bound the wrong quantity in two places, and both produced the same permanent outage. `fs_read` refused a file over `MAX_READ_BYTES` (10 MiB) *on disk* and then emitted up to 4/3 that size as base64, so an ordinary 8 MB file wrote a ~10.7 MB line; `fs_grep` in `output_mode: "content"` bounded **nothing at all** (no line cap, no byte cap -- `fs_find`/`fs_glob`/`fs_list` capped at 200/1000/5000, grep at nothing), so a grep for a common word over a large granted repo did the same with no unusual input. Relay reads a stdio MCP's stdout with a `bufio.Scanner` capped at `bridge.MaxMessageSize` = 10 MiB (`relay/bridge/types.go:13`, used at `external_mcp.go:844`) and treats an over-long token as FATAL: `bufio.ErrTooLong`, `readLoop` exits, `readerErr` latched, no respawn -- **every enrolment on every profile is dead until an operator relaunches Relay.app**. Measured: 6 MB file -> 8,000,099-byte line, fine; 8 MB file -> 10,666,767 bytes, transport dead; 15 MB of grep matches -> 15,923,008 bytes, transport dead (and note the two failure shapes differ from outside -- in the `fs_read` case fsmcp itself dies, in the grep case fsmcp survives and relay's reader dies). `src/limits.ts` holds the numbers and the reasoning: `MAX_RESPONSE_BYTES` = 1 MiB (transport, ~10x under relay's cap, applied to the ENCODED response and to `fs_write`'s inbound `content` -- a request line is a line too), `MAX_BASE64_FILE_BYTES` = 256 KiB (CONTEXT, not transport: base64 tokenizes at ~3 chars/token, so 1 MiB of file is ~460K tokens, twice a standard window; 256 KiB is ~115K), `MAX_RESULT_BYTES`/`MAX_FRAME_BYTES` (the backstops). **`MAX_READ_BYTES`/`MAX_WRITE_BYTES`/`MAX_EDIT_READ_BYTES` are NOT redundant with these and must not be deleted as such** -- they bound the ALLOCATION in a single synchronous process, the wire bounds bound the MESSAGE; issue #16 argues the former "earns its place" and makes all of them operator flags, and both families should exist under it. Sizing is MEASURED with the encoder that will actually run (`wireBytes` = `JSON.stringify` + `Buffer.byteLength`), never estimated: JSON escaping runs from 1x (ASCII) to 6x (a C0 control byte, valid UTF-8, present in real files), so 2000 lines x 2000 control characters -- inside every pre-existing limit -- was a ~24 MB line.
- **Bounded, never silently shortened -- and "refuse" versus "cap and report" is decided by whether the mode promises fidelity.** `fs_read`'s base64 path is a fidelity mode (PR #13: it must round-trip through `fs_write` byte-for-byte), and a base64 payload has nowhere to carry a "there is more" marker without breaking that identity, so an over-ceiling whole-file read is **REFUSED** -- a silent prefix there would be undetectable from the content. `fs_read`'s text mode already had a complete pagination contract (`DEFAULT_LIMIT`, the inline continuation note, `_meta.truncated`, a resume offset) which issue #16 explicitly blesses, so the byte budget is just that bound in a second dimension: the page ends early, says which limit ended it, and names the offset to continue from. `fs_grep`/`fs_glob`/`fs_list`/`fs_find` **cap and report** -- `(showing X of Y ...)` inline plus `_meta.truncated` structurally, with the REAL Y (grepFallback stops collecting past the cap but keeps counting, so it never reports its own cap back as the answer). Refusing is wrong for a search: one that found too much has still done useful work, and `fs_grep` has never claimed fidelity -- it is a view, already filtered, re-ordered, and truncated by `head_limit` and the wall-clock budget. **Do not "fix" fs_grep by making it refuse, and do not "fix" fs_read's base64 mode by making it truncate.** The shared arithmetic is `capLines()` in limits.ts (count AND bytes, reporting which bound bit); the vocabulary stays with each tool.
- **Two backstops, both alarms rather than mechanisms.** `boundResultBytes()` runs in `ToolRegistry.call` next to `redactLeakedHostPaths` and for the same reason -- it replaces any result over `MAX_RESULT_BYTES` outright (never shortens it: at that layer there is no structure left to shorten honestly) with an error naming the tool and saying it is an fsmcp bug. `respond()` in main.ts measures the actual serialised LINE against `MAX_FRAME_BYTES` and substitutes a short JSON-RPC error, because it is the only place that sees the whole frame: `tools/list` and `initialize` never pass through the registry, and `tools/call` appends its dropped/malformed-`_meta` advisory blocks AFTER the registry has looked. Tools are still expected to bound their own results, because only the tool knows how to produce a USEFUL bounded answer.
- **`encoding: "base64"` takes a BYTE window (`byte_offset`/`byte_length`), and it is deliberately not `offset`/`limit`.** Those stay refused in base64 mode (they are line-based and mean nothing against a byte dump), and the new pair is refused in text mode, both for the same reason: silently accepting either would hand back a range the caller did not ask for. The window uses a positional read (`fs.openSync(p, 'r')` + `fs.readSync`), so it allocates the WINDOW and not the file -- which is why base64 mode is now exempt from `MAX_READ_BYTES` and can reach into a file of any size, and why `tests/no-link-primitive.test.js` now allows `fs.openSync` **only** with an `'r'` flag (any other flag creates or truncates and is a sixth mutating primitive needing its own argument). **A windowed read carries no round-trip promise**: `fs_write` has no matching byte offset and no append mode, so windows cannot be reassembled into a file through fsmcp. That is deliberate. Every `fs_write` is one atomic replace (temp file + rename, see atomicWrite.ts) and a file assembled across several calls is by construction not atomic, so a positional write would trade away the guarantee `fs_write` exists to make; byte-exact MOVEMENT of a large file belongs in a copy tool that never brings the bytes through fsmcp at all (issue #12).
- **Byte fidelity is content-based, not extension-based (issue #11).** `fs.readFileSync(path, 'utf-8')` -- the call every one of `fs_read`/`fs_edit`/`fs_grep`'s fallback used -- maps every byte that is not valid UTF-8 to U+FFFD before any of this codebase's own code runs. That mapping is lossy and irreversible the instant it happens: the original byte is gone, and writing the decoded string back (`fs_write`, `fs_edit`) re-encodes each replacement character as three DIFFERENT bytes, silently corrupting the file with no error, warning, or hint anywhere in the path (measured: 4 bytes of latin-1 became 10; 7 bytes of arbitrary binary became 13). The fix is a pass-through principle, not a content judgement: fsMCP does not decide what a file's bytes MEAN -- there is no "this looks like a binary file" heuristic anywhere in this codebase, and in particular no extension-keyed special case (an earlier version of `fs_read` auto-base64'd a fixed set of image extensions; that keyed the decision off a **string**, so two files with byte-identical content and different names behaved differently, and every other non-image binary -- a `.dat`, a latin-1 `.txt`, a UTF-16 file -- still took the lossy path. Removed entirely, not extended, because extending it would mean picking a bigger fixed list instead of fixing the actual question). Instead, every call site that needs to decide asks one question, from the bytes: "can the caller's DECLARED encoding represent these bytes losslessly?" `src/encoding.ts`'s `decodeUtf8Strict()` (`new TextDecoder('utf-8', { fatal: true })`, never `Buffer#toString('utf-8')`, which has no strict mode and is the exact lossy call this issue is about) answers that for UTF-8 text; a hand-rolled byte scanner is deliberately not used in its place, since it would duplicate logic the platform already implements correctly with real ways to get it subtly wrong (an off-by-one on a continuation byte, an overlong encoding accepted). `fs_read` takes an `encoding` argument: `"text"` (default) decodes as UTF-8 and refuses if that fails, naming the file and pointing at `"base64"`; `"base64"` returns the file's exact bytes unconditionally, on any file, decoded or not. `fs_read`'s text mode was already a VIEW before this issue (line-numbered, truncated at 2000 chars per line, `offset`/`limit`-windowed) and is documented as one now rather than implied to be byte-faithful; those view options are meaningless against a byte dump, so `encoding: "base64"` REFUSES `offset`/`limit` rather than silently ignoring them, and returns whole-file bytes with no line numbers and no truncation. **A mode that exists for fidelity must round-trip through itself** (PR #13 review): `fs_read`'s base64 reply (`src/tools/read.ts`) is the BARE base64 payload -- no header, no trailing newline, nothing else in the content string, with the byte count carried structurally in `_meta.bytes` instead -- specifically so `fs_read(base64)` piped straight into `fs_write(base64)`'s `content`, unmodified, is an identity on the file's bytes. An earlier version prefixed a human-readable `"[base64: N bytes]\n"` header; that failed closed rather than corrupting anything (`isValidBase64` refused the header line as malformed base64), but it meant fs_read's own reply was not valid fs_write input, so the obvious composition of the two calls didn't work -- and a caller that "fixed" this by guessing at an unspecified stripping pattern could just as easily strip it wrong and silently corrupt the bytes, reproducing this issue's core failure one level up, looking like a caller bug instead of a design one. Text mode is explicitly exempt from this rule -- it is a documented view (line-numbered, truncated, says so) and never claimed to be an identity. `fs_write` mirrors this: `encoding: "text"` (default, unchanged) writes the UTF-8 encoding of `content` as-is; `encoding: "base64"` decodes `content` as base64 and writes those exact raw bytes (`fs.writeFileSync` with no encoding argument -- passing `'utf-8'` there would re-interpret an arbitrary byte buffer as text, corrupting exactly what this path exists to preserve), after `isValidBase64()` rejects anything outside the base64 alphabet or not block-aligned (Node's own base64 decoder is lenient and silently DROPS invalid characters rather than erroring, which would otherwise let a truncated copy-paste decode to the wrong bytes and still report success). **`fs_write` does NOT refuse U+FFFD in text-mode content** -- a file may legitimately contain the replacement character, and second-guessing the caller's own declared-text content is a content judgement this principle forbids, not a representability question; if a caller writes U+FFFD, that is written, verbatim, like any other character. **A lone (unpaired) UTF-16 surrogate in `content`/`new_string` (possible over JSON-RPC -- `JSON.parse` does not validate surrogate pairing, so a wire string can contain one even though nothing this server itself ever decodes from disk can produce one) IS refused unconditionally, by both `fs_write` and `fs_edit`, with no escape hatch**: this is not a heuristic, because there is no valid UTF-8 encoding for a surrogate code point at all -- Node's encoder would silently substitute U+FFFD for it, the same lossy shape as the rest of this issue, just introduced at the JSON-RPC boundary instead of by a disk read, and refusing has no legitimate case to second-guess since representing it correctly is not possible in the first place. `fs_edit` refuses to operate on a file whose bytes are not valid UTF-8 at all (no base64 mode for it -- a byte-level splice is not a string replacement, and this file does not invent a new operation to paper over that): it is defined over text, and content that is not representable as text has no meaning to find-and-replace against, so refusing is "this operation does not apply," not "binary is dangerous." `fs_grep`'s Node fallback (`grepFallback`) reads with the same `decodeUtf8Strict()` and skips (does not error on) a file that fails it, the same as any other unreadable file -- it only reports, never writes, so there is no write-back to corrupt, but reporting a match against a lossily-substituted line would still hand a caller text that does not match the file with no way to tell; skipping keeps it agreeing with `fs_read` about what it declines to decode. Truncation of an over-long line is flagged twice: the existing inline `"... [truncated]"` marker for a human reader, and `_meta.truncated: true` on the result for a caller that wants to branch on it programmatically instead of pattern-matching English -- a sibling of `_meta.scope_violation` (see below), not a replacement for it; the two never appear on the same result (one is a refusal's `_meta`, the other a success's).
- **fs_move** validates both `source` and `destination` independently and in full (C4), refuses an existing destination unless `overwrite: true`, and refuses moving a directory into (or onto) its own descendant. **Both endpoints are refused as a grant ROOT, for different reasons and with different classifications (issues #24 and #34).** The `destination` is the write half -- fs_move brings that name into being -- so it is a `scopeViolationResult`. The `source` is the DELETE half: `rename(2)` reaches the same outcome `fs_delete` already refuses, so the sandbox root can be moved out of existence with `fs_move { source: "/d0", destination: "/d1/moved-root" }` on a two-root grant -- measured, `/d0` gone, whole tree relocated, audit `ok`. Nothing leaves the grant, which is exactly why neither `checkPathV` nor #24's destination guard sees it. The source refusal is therefore a plain `errorResult` with NO `_meta.scope_violation`: the client addressed something inside its own scope, and that field has to keep meaning "outside" or the one signal an operator alerts on stops distinguishing anything.
- **fs_move makes exactly one mutating syscall -- `rename(2)` -- and no removal syscall at all (issue #23).** It used to implement `overwrite: true` as `rmSync(destination)` followed by `renameSync(source, destination)`: delete first, ask questions never. That one line was three separate data-destruction bugs. **(1)** When the two paths were the SAME directory entry, the unlink took the source's own data and the rename then failed ENOENT with nothing left to move. The everyday trigger is a case-only rename -- macOS ships APFS **case-insensitive** by default, so `meeting.md` and `Meeting.md` are one entry -- and the tool walked the caller into it: the first attempt refused with "destination already exists (pass overwrite: true to replace it)", so obeying fsMCP's own instruction destroyed the file, and relay's audit recorded `tool_error`, which reads to an operator as *nothing happened*. Same shape for a literal self-move, for a `.`-component alias, and recursively when both names were the same directory. **(2)** `overwrite: true` onto a directory destination was an unbounded recursive delete: `mv file dir/`, the POSIX idiom every agent knows, erased a whole tree and logged `ok`. **(3)** Any rename that failed *after* the unlink had already committed left the destination simply gone -- proven live across two real volumes, where a cross-device `overwrite` (EXDEV) deleted the destination file and reported "move failed". The fix is not a fourth guard on top of the unlink, it is the removal of the unlink: `rename(2)` replaces an existing file atomically on its own, so the `rmSync` bought nothing it did not also break. `tests/move-destroys-data.test.js` pins that absence against the source text, the way `tests/no-link-primitive.test.js` pins the absence of link primitives -- a future edit that "just needs to clear the destination first" would pass every behavioural test right up until it did not.
- **Same-entry is decided on `{dev, ino}` from `lstat`, before anything else can happen to either path.** Not `path.resolve` string equality: that does not know the volume is case-insensitive and never will (case folding is a property of the filesystem, and of its Unicode normalization, not of the string), so a lexical check is a guess that is right on Linux and wrong on the platform this ships on. The inode pair is the filesystem's own answer and it settles the case-insensitive, self-move and `.`-alias cases in one comparison instead of three string tests that each miss something. `lstat`, not `stat`, because `rename(2)` operates on directory ENTRIES: following the final component would make a symlink and its target compare equal, and `fs_move <link> -> <its target>` is a real operation, not a self-move to short-circuit (same reasoning as C2 in `fs_delete`). A hard-link pair also shares `{dev, ino}` legitimately; routing it here matches `rename(2)`'s own specified behaviour for that case ("return successfully and perform no other action") and, more to the point, destroys nothing. **A case-only rename is a rename, so it takes the plain-`renameSync` path and does not consult `overwrite` at all** -- it works on the first call, with no flag. Refusing it would not have been a fix: it is an ordinary thing to want, `/bin/mv` does it in one line, and `renameSync` alone already does it correctly on APFS. When the two names also canonicalize to the same string (a literal self-move, a `.` or trailing-slash alias) the result says `nothing to move` instead of claiming a move that did not happen -- as a SUCCESS, because nothing failed and nothing was destroyed, and an error there would be one more audit line that reads as a failure when the truth is "already so". **When they do NOT canonicalize to the same string, the reply no longer says `Moved` either (issue #39), and what it says instead is shaped by something fsMCP cannot do.** A hard-linked pair took this branch, `rename(2)` correctly did nothing, and the reply was `Moved a.txt to b.txt` with audit `ok` while both names still sat there unchanged -- an agent that believes it has moved a file and then acts on that belief is the failure mode. The mechanism was right and does not change; only the sentence was wrong. The constraint: **fsMCP cannot tell a hard-linked pair from a case-insensitive alias from `lstat` alone**, and `nlink` is not a discriminator -- it is 2+ for a hard-linked pair AND for a case alias of a file with a hard link anywhere else, and it says nothing about whether the other link is the destination this call named (`nlink === 1` would rule the hard-link case out, but a message precise in one branch and vague in the other trains a reader to read the vague branch as the precise one, and the value is racy anyway). `canonicalizePath` does not fold case either -- measured on APFS, `.../A.txt` resolves to `.../A.txt` when the entry on disk is `a.txt` -- which is exactly why a case alias reaches this branch rather than the `nothing to move` one. For a case alias the rename genuinely happened; for a hard link it genuinely did not. So the message **asserts neither and states both**, and points at the one thing that does settle it after the fact and that the caller can observe with the tools it already has: the directory listing (a case-only rename leaves one entry, a hard-linked pair leaves two). Still a SUCCESS, for the same reason the `nothing to move` branch is. **The same-entry branch continues to run BEFORE the `overwrite` guard, and that ordering is the point rather than an oversight** (#39 asks): `overwrite` gates DESTRUCTION, and on this branch there is nothing to destroy -- the destination IS the source -- so demanding the flag would be asking permission to destroy a file when the only file involved is the caller's own source, which is precisely the sentence #23 removed after obeying it destroyed the data.
- **A directory destination is refused, and `overwrite: true` is not a way around it.** This is the deliberate answer to issue #23's second defect, and the POSIX reading (silently move *into* the directory, the way `mv file dir/` does) was considered and rejected: it makes the meaning of `destination` depend on the state of the filesystem at call time -- "the new name" usually, "the parent of the new name" when something happens to be a directory there -- so relay's audit would record an argument that is not where the data went, and `overwrite: true` would end up governing a path the caller never named. Refusing costs the caller one corrected call, and the refusal names it for them: it prints the full `<destination>/<basename(source)>` address, because the whole shape of this bug was a refusal that talked the caller into a destructive call instead of the correct one. For the same reason the no-flag refusal for a directory destination does NOT say "pass overwrite: true" -- pointing at a flag that will not, and must not, do what it says is how defect 1 happened. The one directory destination that is allowed is an EMPTY one being replaced by another directory: `rename(2)` does that atomically and it destroys nothing, which is the rule rather than an exception to it. **No new flag was added** (`replace_directory`, a mirror of `fs_delete`'s `recursive`): destroying a directory tree is `fs_delete`'s job, it already has the `recursive` opt-in and the 10,000-entry cap, and routing the destruction there means the audit log records a *deletion* when a deletion happens instead of a line that says only "Moved". **That is also the argument for why `fs_delete`'s 10,000-entry cap has no counterpart here**: a cap bounds a recursive walk that is about to be removed, and fs_move has no recursive delete to bound -- it removes exactly zero directory entries and creates exactly one, and the kernel itself refuses ENOTEMPTY rather than let `rename(2)` replace a directory with contents.
- **fs_move does not fall back to copy-and-delete across filesystems (EXDEV).** A grant can legitimately span two volumes (two `--allowed-dir`s, or a mount underneath one), and `rename(2)` cannot cross that boundary -- verified on a real second volume, not reasoned about. The EXDEV case is named explicitly in the error rather than left as a bare errno, and the message states that nothing was changed, which is now true: both endpoints survive, where before the unlink had already destroyed the destination by the time EXDEV was returned. A copy-then-delete fallback would be a different operation wearing rename's name -- non-atomic, unable to preserve for free what rename preserves (inode, hard links, xattrs, permissions), able to leave a half-copied file behind on failure, and it would put a delete back inside fs_move, which is exactly what this issue was about. A caller who wants the bytes on the other volume can compose the tools that already exist and are each audited on their own: `fs_read` + `fs_write` in `base64` mode (an identity on the bytes, see the encoding section above), then `fs_delete`.
- **fs_delete** refuses to remove an `allowed_dir` root itself (the remove half of the grant-root rule above -- same words, deliberately NOT a `scope_violation`), defaults `recursive` to `false`, caps a recursive delete at 10,000 entries (refusing past it rather than truncating silently), and relies on `fs.rmSync`'s recursive mode unlinking a symlink it meets rather than following it -- pinned by test, not just assumed.
- **TOCTOU is a documented non-goal (C7),** for every mutating tool including the new ones: winning the check-then-use race requires writing a symlink inside an allowed directory, which the same uid running fsmcp could already do directly. If fsmcp ever runs more privileged than whoever can write into an allowed dir, the fix is `openat`-per-component with `O_NOFOLLOW` from a pinned root fd, not a better check.
- **The atomic replace preserves the mode, the xattrs and the ACL -- and nothing else -- on purpose (issue #20).** `writeFileAtomic` renames a temp file over the target, so the file that survives is a NEW INODE carrying only what this function deliberately put on it. The first version of that fix put the permission bits there and stopped, and both halves of what it did were wrong. (1) **It did not preserve the mode.** It passed the old file's `st_mode` to `fs.writeFileSync`'s `mode` option to stay inside the five-call mutating surface `no-link-primitive.test.js` pins -- and that option is `open(2)`'s `mode`, which the process umask masks. Measured under the macOS default `umask 022`: a 0664 file came back 0644 and a 0777 file came back 0755, so a group-writable file in a shared folder silently stopped being group-writable on the agent's first edit. `chmod(2)` does not consult the umask, so the fix is `fs.chmodSync` on the temp file -- the sixth call in that surface, spent deliberately, with its containment argument written into `no-link-primitive.test.js` next to the assertion that now expects it. The lesson generalises: a syscall budget that produces a wrong answer is not a constraint being honoured, it is a bug with a rationale attached. (2) **It destroyed extended attributes and ACLs**, which on macOS means Finder tags, Finder comments, Spotlight metadata and `com.apple.quarantine` -- gone on every fs_edit/fs_write, on a success result, with a clean `ok` in the audit log. Node has no binding that can carry them: no `listxattr`/`getxattr`/`setxattr` in `fs`, no ACL API, no FFI, and `fs.copyFileSync` was measured to preserve neither (with or without `COPYFILE_FICLONE`), so widening the forbidden-primitive list would have bought a banned call that does not even work. macOS's own answer is `copyfile(3)` with `COPYFILE_XATTR | COPYFILE_ACL`, and `/bin/cp -p` is that call with a command line in front of it: the temp file is seeded as a `cp -pN` of the target and then has its content written over it, which works because truncating a file does not clear its xattrs or its ACL. Rejected on the way: `cp -c` (clonefile, O(1) on APFS and the obvious way to avoid re-copying the old bytes) silently drops the ACL -- measured -- so it buys speed with exactly the metadata this change exists to keep; and an `xattr(1)` loop plus `ls -le` piped into `chmod -E` makes fsmcp a parser of `ls`'s human-readable output and round-trips ACEs through a text form that demonstrably loses information. The spawn is contained by construction and pinned by test: absolute program path (not PATH -- unlike `rg`, which is optional and has a Node fallback, a shadowed `cp` here would decide what happens to a granted file), literal argv array, exactly two operands, both of which `writeFileAtomic` owns (`to` is its own random temp name, `from` is the path every caller already put through `checkPathV`/`canonicalizePath`), no `-R`, no `-l`/`-s`. It is skipped entirely for a new file and for anything that is not a regular file -- `cp` on a FIFO would read the FIFO and hang this single-threaded server forever. **What is still NOT preserved, deliberately:** hard links (rename installs a new inode; the sibling name keeps the old one and the old content -- that IS atomic replace, and the alternative is the truncate-then-write that loses the file), setuid/setgid/sticky (the `& 0o777` mask, now load-bearing because `cp -p` DOES copy setuid onto the temp file), BSD file flags (`cp -N`: copying `uchg` onto the temp file would make it unwritable AND unremovable, stranding it inside a granted directory), and ownership/old timestamps. **macOS only, no-op elsewhere:** the `-p` guarantee is BSD `cp`'s, GNU `cp -p` means something narrower and has no `-N`, and Linux ACLs are a different mechanism -- shipping an argv that cannot be verified on the platform it targets is not portability, so other platforms keep their previous behaviour and the gap is documented rather than papered over. **If the attributes cannot be READ, the write is refused**, not performed lossily: fsmcp cannot preserve metadata it cannot enumerate, and destroying it while reporting `ok` is the one outcome ruled out.
- **No throws across tool boundary** -- registry wraps handlers in try/catch as a backstop, but tools are expected to check cleanly (absolute path, NUL bytes, overlong paths -- all centralized in `security.ts`) rather than lean on the catch.

## Adding a Tool

1. Create `src/tools/foo.ts`
2. Export `registerFoo(registry: ToolRegistry)`
3. Define tool with `registry.register({ name, description, inputSchema, category, annotations }, handler)` -- `annotations: { readOnlyHint, openWorldHint }` is required on the type, not optional; set both explicitly and honestly
4. Use `schema()`, `stringProp()`, `intProp()`, `boolProp()`, `enumProp()` from registry. For any path ARGUMENT's description (`file_path`/`path`/`source`/`destination`), use `virtualPathDescription()` (registry.ts) instead of writing your own -- it is the one place that describes the `/<label>/...` address shape without asserting a concrete label (labels are assigned per call, not known when this static schema is built), and every existing tool's path argument goes through it so they stay worded identically. Writing "Absolute path to the file" by hand here is the exact regression a schema-text test (`tests/schema-text.test.js`) exists to catch: that was true before issue #7 and became actively misleading after it.
5. Return via `textResult()` or `errorResult()` from types; use `scopeViolationResult()` (or `checkPath()`/`checkPathNoFollowFinal()` from security.ts, which return it for you) for any refusal that means "outside your scope". If the tool WRITES, CREATES or REPLACES anything at a caller-supplied path, `checkPathV()` alone is not enough -- a grant root passes it, because a root is inside itself -- so also call `refuseAllowedDirRootWriteV(hostPath, ctx.allowedDirs, '<verb>', ctx.labels)` (vpath.ts) on that path, immediately after the containment check and before any syscall (issue #24). If it creates DIRECTORIES -- `fs.mkdirSync(..., { recursive: true })`, or anything else that walks up to a parent that exists -- add `refuseMissingAllowedDirRoot(hostPath, ctx.allowedDirs, '<verb>')` (security.ts) right after it, wrapped in `translateResult(result, ctx.allowedDirs, ctx.labels)`, or the recursive create runs past the grant root whenever that root does not exist (issue #33). That refusal is a plain `errorResult()`, NOT a scope violation: the caller addressed its own grant, and the grant is what points at nothing
6. Accept `ToolContext` as second arg. For any path ARGUMENT the client supplies, call `decodeInboundPath(arg, ctx.labels)` (vpath.ts) first and use the host path it returns -- not the raw argument -- for everything after. Check that decoded host path with `checkPathV()`/`checkPathNoFollowFinalV()` (vpath.ts) -- not `checkPath()`/`checkPathNoFollowFinal()` (security.ts) directly, or the refusal message will still name the host path, and not `validatePath()` + `errorResult()` by hand, or the refusal won't carry `_meta.scope_violation` when it should. A path the tool itself PRODUCES (a search hit, a directory listing entry) needs `hostToVirtualOrRedact()` (vpath.ts) on the way out, and then `escapePathField()` (resultFormat.ts) if it is going into a line-oriented text result -- in that order, since escaping first would change the string the outbound prefix match runs against. State the rules in the description with `pathFieldEscapingRules()` and `RESULT_TRAILER_RULE`; a format whose escaping is unstated is not parseable (issues #31, #37). Any OTHER message that embeds a path this handler already decoded (a success sentence, a `file not found`) must be wrapped in `translateResult(result, [thatPath, ...], ctx.labels)` before it is returned -- outbound translation is deliberate per call site, not automatic (see "Outbound translation is deliberate" above); a caught exception's message should go through `describeError(err, ctx.labels)` instead of `err.message` directly, so `err.path`/`err.dest` get translated. Never pass a tool's own file CONTENT (what `fs_read` returns, or a matched line in `fs_grep` content mode) to any of these -- it is not a path, and translating it would corrupt it (PR #10)
7. If the tool can produce an unbounded result -- a listing, a search, anything whose size is decided by what is on disk rather than by the arguments -- **bound it yourself, in wire bytes as well as in items**, with `capLines()` (limits.ts) and report the bound the way every other tool does: `(showing X of Y ...)` inline AND `_meta.truncated: true` structurally, with the real Y. The registry backstop (`boundResultBytes`) will catch you if you don't, but it can only kill the whole result and say "this is a bug in fsmcp" -- it has no way to give the caller a useful partial answer. A count-only cap is not a bound: `fs_list`'s 5000 entries at PATH_MAX names is over 5 MB (issue #19)
8. Import and call `registerFoo(registry)` in `main.ts`
