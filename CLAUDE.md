# fsMCP

MCP server providing file system tools via stdio. 10 tools, 1 category. TypeScript/Node.js. One runtime dependency (glob). No shell: nothing here reaches `execSync` or a shell string; `execFileSync` with an argv array is the only way this process ever spawns anything (ripgrep, for `fs_grep` and `fs_find`).

## Architecture

Single-threaded stdin/stdout MCP server. Newline-delimited JSON-RPC 2.0. Protocol version `2024-11-05`.

```
src/
  main.ts        Stdin loop, JSON-RPC dispatch (initialize, tools/list, tools/call), _meta narrowing (C1)
  types.ts       Wire types, MCPTool interface, result helpers (textResult, errorResult, scopeViolationResult)
  registry.ts    ToolRegistry class + JSON schema builder helpers
  security.ts    Path validation against allowed_dirs (_meta + CLI flags), _meta narrowing rule
  vpath.ts       Virtual <-> host path translation (issue #7), layered on top of security.ts, never inside it
  tools/         One file per tool, each exports register(registry)
```

Entry point reads stdin line-by-line, dispatches to `ToolRegistry`, writes JSON to stdout. Synchronous.

## Tools

All ten tools are category "File System" -- there is no second category any more (the old "Shell" category, and `fs_bash` with it, is gone: see "fs_bash removal" below).

| Tool | Read-only | Backend |
|------|-----------|---------|
| fs_read | yes | fs.readFileSync (raw bytes), strict UTF-8 decode, cat -n format |
| fs_glob | yes | glob npm package, mtime sort, 1000-result cap |
| fs_grep | yes | ripgrep (rg) with Node.js fallback, wall-clock budget |
| fs_list | yes | fs.readdirSync, one directory, non-recursive, 5000-entry cap |
| fs_find | yes | `rg --files --no-follow` (Node walker fallback) + in-process fuzzy scoring, 200-result cap |
| fs_write | no | fs.writeFileSync (text or base64 bytes), auto-creates dirs |
| fs_edit | no | split/join literal string replacement, UTF-8 text only |
| fs_mkdir | no | fs.mkdirSync, recursive defaults true |
| fs_move | no | fs.renameSync, both endpoints validated |
| fs_delete | no | fs.unlinkSync (symlinks/files) or fs.rmSync recursive (directories), 10000-entry cap |

relay's `access: read` grant admits only tools with `readOnlyHint: true` (exact-key lookup; absent/null/malformed reads as mutating), so this split is what makes a read-only profile a one-field decision instead of an `allowed_tools` list an operator has to keep correct by hand. `destructiveHint`/`idempotentHint` are not consulted by relay -- don't rely on them for gating.

### fs_bash removal

`fs_bash` (arbitrary shell, `readOnlyHint: false`, `openWorldHint: true`) is gone, not fixed. `allowed_dirs` was never a boundary for it -- a command reaches any path with or without a `cd` -- and every containment guarantee the rest of this server makes was void while it was registered. Removing it also removed the module-level `currentCwd`, the only cross-call mutable state fsmcp ever had.

## Key Patterns

- **Tool = module** with `export function register(registry: ToolRegistry)`. Handler signature: `(args, ctx) => MCPCallResult`.
- **ToolContext** carries `allowedDirs`, computed once per call in `main.ts` by `narrowAllowedDirs()` (security.ts) from `_meta.allowed_dirs` (relay per-call context) and `--allowed-dir` CLI flags -- **never** a plain union of the two. See "C1: `_meta` may only narrow" below. It also carries `labels: LabelEntry[]` (types.ts), this call's virtual-space labels for `allowedDirs`, in the same order -- see "Virtual path space (issue #7)" below.
- **contextSchema v2**, declared in `initialize`'s `serverInfo`, alongside `contextSchemaVersion: 2`:
  ```json
  "contextSchema": {
    "allowed_dirs": {
      "type": "array", "items": { "type": "string" },
      "description": "Directories this client may read, search and modify within",
      "scope": "restrict", "source": "operator",
      "applies_to": ["fs_*"], "enumerable": false,
      "disclose": "count"
    }
  }
  ```
  Every keyword here is load-bearing and must stay byte-exact: absent `contextSchemaVersion`, relay parses this as v1 (looks for a field literally named `allowed_dirs`, derives it from the project path) -- and a **remote** access profile has no project path, so a v1 fsmcp cannot be granted to one at all. `source: "operator"` (not `"project_path"`) is the fix: an operator types the roots instead of relay deriving them. `enumerable: false` because fsmcp cannot offer candidate directories without listing the host's filesystem to whatever UI renders them. No `ui` key -- ignored under v2, and it was stale under v1 too. `disclose: "count"` (relay#33, fsmcp#15) governs what relay renders into the scope note it appends to every governed tool's DESCRIPTION -- the last surface still carrying a host path after issue #7, and the one a live Hermes run read the sandbox root out of. Its spelling fails silently in both directions: `"Count"` makes relay refuse the whole schema (every fsmcp tool withheld from every grant), an unrecognised word is ignored and the value renders anyway. A relay predating relay#33 ignores the key and renders the value; fsmcp cannot detect that and does not claim otherwise.
- **C1: `_meta` may only narrow, never widen.** `_meta` is a field relay populates from context configured elsewhere in the chain, but fsmcp cannot verify anything upstream enforced anything, so it treats `_meta.allowed_dirs` as caller-supplied, same as any other wire argument. `narrowAllowedDirs(cliDirs, metaDirs)` implements the whole rule in one place: CLI+meta both set -> **intersection** (each `_meta` dir kept only if it canonicalizes inside some CLI dir; the rest are dropped and reported on the result, not swallowed); CLI set, meta absent -> CLI; CLI absent, meta set -> meta (relay-mediated mode); both absent -> empty, i.e. deny all. "Absent" vs "present but empty" matters and is preserved from `params._meta?.allowed_dirs` through to this function -- collapsing them with `?? []` is what let a plain union stand in for this table before.
- **The dropped-`_meta`-entries report (`main.ts`, appended to every result whose call supplied a `_meta.allowed_dirs` entry that failed the C1 containment check) tells the client the FACT and the COUNT; the entries themselves go to stderr, for the operator.** Fixed in issue #30/#26's cluster; the reasoning below is kept in full because the history is the useful artefact. It used to echo those entries as raw host-path text, on a SUCCESS result, entirely outside `vpath.ts`'s translation and outside `redactLeakedHostPaths`'s `isError`-scoped backstop (it is appended after both). That was accepted deliberately, but **the reasoning recorded here for accepting it was wrong on both halves, and the fsmcp#15 review disproved it by running it.**

The claim was that the echoed entries are "either plain CLI directories or the literal strings a caller's OWN `_meta.allowed_dirs` supplied". Only the second is possible -- `narrowAllowedDirs` (`security.ts`) pushes nothing but `metaDir` values into `droppedMetaDirs`, so a CLI directory can never appear there.

The load-bearing claim was that **a relay-mediated client cannot reach this at all**, on the grounds that relay builds `_meta` wholly server-side from `stored.Context[extID]` and never forwards anything a client sent. The premise is true and the conclusion does not follow. Server-side is not the same as in-scope: if the MCP is registered with `--args --allowed-dir /A` while the profile's `allowed_dirs` also names `/B`, relay sends `["/A","/B"]`, `/B` fails the C1 containment check, and the report echoes **`/B`** -- an operator-configured host path the client was never granted -- on a success result, to a remote client, over the wire. Reproduced:

```
$ printf '%s\n%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"fs_read",
     "arguments":{"file_path":"/d0/a.txt"},
     "_meta":{"allowed_dirs":["/tmp/f2/A","/tmp/f2/B"]}}}' \
  | node dist/main.js --allowed-dir /tmp/f2/A | tail -1
... {"type":"text","text":"[fsmcp: _meta.allowed_dirs entries were dropped because
    they are not contained within any --allowed-dir root: /tmp/f2/B]"}
```

The oracle argument (can a caller confirm a guessed host path by whether it gets dropped?) still stands on its own: over bare stdio the caller is a local principal who can read the disk anyway. What does not stand is the claim that relay-mediated deployments are out of reach. That made it a live disclosure surface that `disclose: "count"` does not reach, and it got its own issue (fsmcp#26).

**The fix, and why it had to be at the point of production rather than behind a backstop.** No backstop can reach this even in principle: **a dropped directory is by construction not in `ctx.labels`**. `redactLeakedHostPaths` works by knowing the granted roots and matching against them, so widening it past `isError` (which would reintroduce the PR #10 content-corruption hazard for nothing) still would not catch a path that is precisely one that was NOT granted -- there is nothing to translate it to. The message simply has to stop naming the path.

So `main.ts` now splits it the way `assignLabels`' duplicate-label refusal already does: **stderr gets the detail** (the entries, in full, on the stream a stdio MCP's host collects a child's diagnostics on, which is not the protocol stream and cannot corrupt a response) because the operator is the only party who can reconcile a CLI floor with a profile and the only one entitled to the paths; **the client gets the fact and the count** (`"...entries were dropped because they are not contained within any --allowed-dir root -- N of them"`), for the same reason `disclose` is `"count"` and not `"none"`: an agent that cannot see that it is confined behaves worse, not better, but it does not need the host's directory layout to know its effective scope is narrower than the one it was sent. The client can do nothing with the paths in any case -- it cannot fix a registration.

**Deliberately a note, not a refusal**, which is where this parts company with the duplicate-label case it otherwise copies. The two look alike and are not. A duplicate label leaves the address space with **no correct reading** -- a `/<label>/…` path names two different files, and picking one hands a caller the wrong file's bytes -- so refusing every call is the only answer that is not a guess. This narrowing has exactly one reading, it is the one C1's own table specifies, and it is already fail-closed: the effective scope is the intersection, which is the safe end of the disagreement, not a coin flip between two. Refusing would turn an operator's over-tight CLI floor into a total outage of a capability whose surviving grant is still valid, and it would fire on the ordinary intended shape of "the operator tightened the floor". If this ever needs to be louder, the levers are the stderr line and relay's own scope note -- which currently renders the profile's count rather than the effective one, and is filed against relay -- not a refusal fsmcp cannot tell apart from correct use.
- **Virtual path space (issue #7): `vpath.ts` is a translation layer on top of `security.ts`, never a replacement for it.** A client addresses paths as `/<label>/…`, never a host path -- `decodeInboundPath(virtualPath, ctx.labels)` turns that into the exact host-path string every tool has always validated, by literal string concatenation (deliberately not `path.join`, which would lexically collapse a `..` before `canonicalizePath`'s kernel-style walk ever saw it -- see the function's doc). Every tool handler calls this immediately after reading a path ARGUMENT (`file_path`/`path`/`source`/`destination`) and before calling `checkPathV()`/`checkPathNoFollowFinalV()` (vpath.ts wrappers around security.ts's own `checkPath`/`checkPathNoFollowFinal`, which run completely unmodified and still decide -- the wrapper only translates the message).
- **Outbound translation is deliberate, per call site, never a whole-result scan.** An earlier version of this ran every result (success AND error) through a single blanket rewrite in `ToolRegistry.call`, replacing any occurrence of a granted host directory with its label. PR #10 review found that this was too broad in three ways: (1) it scanned `fs_read`'s own file content and `fs_grep`'s content-mode matched lines, so a file whose bytes happened to contain the sandbox's real path came back silently corrupted, not translated -- confirmed with a write-then-read byte round trip; (2) the "not a valid address" refusal echoed the caller's rejected argument, and that echo passed through the same rewrite, so a CORRECT host-path guess came back rewritten to its label while a wrong one came back verbatim -- a working oracle for exactly the thing issue #7 exists to close; (3) it was applied incidentally (fires whenever a result happens to contain a matching substring) rather than as a decision made at each site, which is itself a reason not to lean on it. Fixed by translating each known path at its own construction site instead: `translatePathIn(text, hostPath, labels)` replaces one SPECIFIC, already-known path substring (never a scan for anything host-directory-shaped), `translateResult(result, hostPaths, labels)` applies it across a result for the path(s) a tool handler already has in scope, and `describeError(err, labels)` rebuilds a caught exception's message using Node's own `err.path`/`err.dest` (a `NodeJS.ErrnoException`'s structured properties, not text-mined from `.message`). The decode-refusal message no longer echoes the caller's argument at all. `ToolRegistry.call` keeps a narrow backstop, `redactLeakedHostPaths()` -- scoped to `isError` results ONLY, so it can never touch `fs_read`/`fs_grep`-content success payloads -- which replaces an entire result with a generic "this is a bug" message if a granted host directory somehow still leaked through; an alarm, not a translation mechanism.
- `fs_glob`/`fs_find`/`fs_list` translate each output path individually via `hostToVirtualOrRedact()`, which **redacts** (a placeholder string) rather than emits a path that cannot be mapped to any granted label -- that case would mean a path reached output from outside the grant, which is a bug security.ts's own checks should already have prevented, not a value this layer can make sense of.
- Labels: `label=/abs/path` in an `allowed_dirs` entry (CLI or `_meta`, stripped by `stripLabels()` before the bare host path ever reaches `narrowAllowedDirs`/`validatePath` -- an unstripped `"label=/x"` is not absolute and would otherwise resolve against fsmcp's own CWD) wins; otherwise `d<N>` by position in the call's *effective* (already narrowed) scope. `_meta.allowed_dirs` and `--allowed-dir` themselves are unchanged: still plain host-path strings, still operator/relay-side.  **A duplicate label refuses the whole call, fail closed** (`assignLabels`, vpath.ts): `virtualToHost` resolves a label with `Array.prototype.find`, which silently returns the first match, so two directories sharing a label would not error on their own -- it would quietly make the second unaddressable and make `fs_glob`/`fs_find`/`fs_grep` report the identical virtual path for two different files, with `fs_read` of that path always landing on the first-registered directory. Reachable from two explicit `label=`s, or from an explicit `label=` colliding with another entry's auto-assigned `d<N>` (`--allowed-dir d1=/x --allowed-dir /y --allowed-dir /z`: `/y` is position 1, so it auto-assigns `d1`, colliding with `/x`'s explicit one -- a shape no operator would predict from their own flags in order). This codebase already refuses this SHAPE of ambiguity elsewhere rather than picking a winner (`fs_edit` on a non-unique `old_string`, `validatePath` on an empty scope), so `assignLabels` returns an `MCPCallResult` refusal instead of `LabelEntry[]` when it detects one. **That refusal names only the LABEL to the client; the two colliding directories go to stderr, for the operator** -- this file used to record the opposite ("naming both colliding directories -- safe, because both are always either a CLI directory or an already-narrowed `_meta` entry the caller itself supplied"), and that argument holds for the standalone CLI case and fails for the deployment this server exists for, where `--allowed-dir` is not passed at all and the whole scope arrives through `_meta` that **relay** populates from an operator's stored context. In that shape the colliding directories are the operator's host paths and the reader is the one party issue #7 exists to keep them from. The label alone is also the more useful half for each reader: a client cannot fix the configuration, and an operator needs both paths and has stderr. `main.ts`'s dropped-entry report (above) follows the same split, for the same reasons. `main.ts` returns that refusal directly, before `registry.call` ever runs, so every tool fails closed under a colliding configuration, not just an `fs_read` of the ambiguous address. The SAME directory landing on the SAME label twice (a literal duplicate `--allowed-dir`) is redundant, not ambiguous, and is not refused.
- **Scope refusals carry `_meta.scope_violation: true`.** `checkPath()`/`checkPathNoFollowFinal()` (security.ts) wrap `validatePath`/`validatePathNoFollowFinal` and return the ready-made `MCPCallResult` a tool handler should return directly -- `scopeViolationResult()` (types.ts) when the refusal is "outside your scope" (including the empty-scope case), plain `errorResult()` for everything else (bad regex, file not found, malformed path). Relay's audit reads this off a `tool_error` result as a field on that outcome, not a distinct outcome of its own -- it's what lets an operator's audit log tell "the sandbox held" apart from "the tool broke."
- **security.ts** validates paths via `validatePath()` -- resolves symlinks, checks prefix against allowed dirs. Empty allowed dirs = refuse everything (fail closed, not "no restrictions"); an operator who wants unrestricted access passes `--allowed-dir /` explicitly. NUL bytes and paths over `PATH_MAX` are refused up front (`basicPathError`), so they're clean refusals rather than an exception thrown three stack frames into `fs.lstatSync`.
- **Path resolution is component-by-component, not `realpath`-or-lexical.** `canonicalizePath()` walks from the root, follows every symlink in the part that exists, and carries only the not-yet-existing tail lexically. `fs.realpathSync` is all-or-nothing and throws for a path whose last component does not exist -- the ordinary case for `fs_write` -- and the old lexical fallback left symlink components in the string, so a symlink inside an allowed dir pointing outside it let a *new* file be written outside the sandbox. Two things the obvious "realpath the parent" shortcut still gets wrong: `..` must be applied to the resolved path, never collapsed lexically first (`<allowed>/sub/link/../../x` reads as `<allowed>/x` but lands outside -- and `fs.realpathSync` itself normalises `..` lexically, so this leaked *existing* files too), and a **dangling** symlink must be followed via `lstat`/`readlink` rather than treated as absent, because a write through it still creates the file at its target. Do not rewrite this function; extend around it.
- **`validatePathNoFollowFinal()` (C2)** exists for `fs_delete` alone: it canonicalizes `dirname(path)` as usual but re-joins `basename(path)` un-followed, so deleting `<root>/link-out` (a symlink pointing at, say, `/etc`) refuses or succeeds based on the *link* being in scope, never on where it points. `fs_delete` then uses `lstat`/`unlink` on that exact path -- never `stat`, or the same follow happens one line later.
- **Tool output that is a path is re-validated.** `fs_glob`, `fs_find` and `fs_grep` all filter every hit through `validatePath` rather than trusting descendants of a validated directory: whatever walks the tree chooses what gets reported, so a symlink inside an allowed directory that points outside it can come back as an in-scope-looking path. `fs_list` does not recurse, so it has no such gap: every entry it reports is `path.join(validatedDir, entry.name)` for a name `readdir` produced, which cannot contain a separator or `..`.
- **`fs_list`'s record is `type\tsize\tmtime\tpath`, one line per entry, and both halves of that sentence are now enforced rather than assumed.**
  - **The path field is backslash-escaped** (issue #31): a literal backslash as `\\`, and the three characters that carry structure here as `\n`, `\r`, `\t`. Nothing else is escaped, and no other field is (type, size and mtime are all generated). A filename containing a newline is legal on every POSIX filesystem including APFS -- and creatable through fsMCP's own `fs_write`/`fs_move` -- and was emitted raw, so one entry became two lines: a phantom record with no type or size, and a real record truncated at the newline. Nothing errored; the format silently stopped being the format, in the caller's parser rather than here. **The backslash pass runs first and unconditionally**, which is the only reason the scheme is reversible: without it a file literally named `a\nb` and a file whose name contains a real newline emit identical bytes, and a caller unescaping would conjure a newline into a name that never had one. That is also the one behaviour change for ordinary paths -- a backslash in a path now comes out doubled. The **tool description states all of this, including the left-to-right decoding order**, because an escaping scheme a caller is not told about replaces one silent parsing failure with a different one. Escaping was chosen over skipping such an entry (which would make a real, reachable file invisible to the one tool whose job is to say what is there, while every other tool still operated on it happily) and over emitting structured content (the clean answer, and a much larger change worth making only if these tools are reworked as a group). **`fs_glob`, `fs_find` and `fs_grep` have the same exposure and are NOT fixed** -- they all `join('\n')` a list of paths with no escaping. The scheme above is adoptable by `fs_glob`/`fs_find` unchanged (a path per line, nothing else on it); `fs_grep`'s `path:line:content` mode needs a decision about the `:` delimiter and about matched content as well, so it is not a pure copy.
  - **A symlink's size is reported as `0`** (issue #28). `listOneDir` uses `lstat`, which is correct -- it must not follow the link -- and printed `st.size`, which **for a symlink is the byte length of the target path string**. The size column was therefore an exact measurement of a path the client is not allowed to know exists, on the one entry type where every other surface refuses to say anything at all (`fs_read` of that same link is "outside allowed directories"). A few bits on its own, worth more against a guessable prefix: a `latest -> /Volumes/Backup/2026-08-26-nightly` shape is ordinary in a real tree and its length confirms or eliminates a candidate host path in one call, and `fs_move` lets a client rename links freely, so links are cheap to enumerate. Zero costs nothing, because a link's own size is not the size of anything a caller can read. The doc comment above `listOneDir` asserted the containment property this only now has -- "disclosed only as a name and a type", while the size column was disclosing the target's exact length -- and has been corrected to describe the code.
- **fs_grep** shells out to `rg` if available, falls back to recursive readdir + RegExp; both paths are bounded by `grepBudgetMs()` and both re-validate every path before it reaches the caller. The `rg` path always passes `--json` (never `-l`/`-c`/`-n`), parsed by `formatRgJson()`: issue #7 needed something to reliably split "this substring is the path" from "this substring is the file's own content" in order to translate only the former, and the old plain-text parsing (`path:line:content`, regex-anchored on the numeric line number because content can itself contain colons) was already flagged as fragile for an unusual filename -- building a rewrite step on that fragility would have made it load-bearing in a new way. `--json` gives the split structurally (`data.path.text` vs `data.lines.text`) instead. `-c`/count cannot be combined with `--json` (verified against a real ripgrep: it silently reverts to `-c`'s own plain output), so count is derived from each file's `end` event (`stats.matched_lines`) instead. The Node fallback (`grepFallback`) builds its own output strings from paths it already controls, so it needs no JSON round-trip -- but it does need `hostToVirtualOrRedact` on every path it emits (an optional `labels` parameter, threaded from `ctx.labels` at the real call site and left `undefined` for the ReDoS-budget unit tests that have no concept of labels at all). An earlier version of this reasoned that `ToolRegistry.call`'s generic outbound pass (`redactLeakedHostPaths`) would cover it instead; that pass is scoped to `isError` results only (see "Outbound translation is deliberate" above), and an ordinary successful search is never an error result, so the sandbox's real absolute path came back unmodified in every output mode on any host without ripgrep on PATH -- fixed by translating each path at grepFallback's own three emission sites, the same as everywhere else in this file. Matched line TEXT in content mode (`lines[idx]`) is never touched, for the same reason `formatRgJson`'s `lines.text` and `fs_read`'s own bytes are not. **`grepWithRg`'s catch-all error branch (`grep error: ${detail}`, built from `rg`'s own `stderr`/`.message` text) is a known, accepted exception to "every path goes through `describeError`": ripgrep's free-text errors are not structurally split into path/content the way `--json` output is, so there is no `.path`-shaped field to translate, and correctness here currently leans entirely on `redactLeakedHostPaths`'s `isError`-scoped backstop catching a granted directory if `rg` happens to print one verbatim (confirmed live: a stub `rg` erroring with the sandbox root in its stderr came back redacted, not leaked). That is a real gap, not a false alarm -- if a later change adds a new `rg` flag (`--follow`, a new output mode, anything that changes what `rg` writes to stderr on failure) whose error text could embed a host path in a shape the backstop's exact-substring match does not catch, this branch is where that leak would resurface. Parsing ripgrep's own error text to close it is exactly the fragility this file moved off of when `--json` replaced plain-text output for matches; treat any change here as a reason to re-verify this specific branch against a real failing `rg`, not as license to assume the backstop always saves it.**
- **fs_find** = `rg --files --no-follow` (Node walker fallback, which skips every symlink outright) + in-process fzf-style subsequence scoring (contiguity + word-boundary bonuses) over the resulting, re-validated file list. No new dependency -- `glob` stays the only runtime one.
- **fs_edit** uses `split().join()` for literal matching (no regex special char issues), and **refuses both of that primitive's degenerate inputs up front, before the file is read** (issue #30). `content.split("")` splits into CHARACTERS, so an empty `old_string` counted `length - 1` phantom occurrences and `parts.join(new_string)` interleaved the replacement between every character of the file: `hello` was written back as `hXeXlXlXoX` and reported as `Replaced 5 occurrence(s)` on a success result, with relay's audit recording `ok`. The un-flagged path was the worse half -- `old_string found 5 times. Use replace_all or provide more context to make it unique` is a sensible sentence about a real string and a nonsense one about an empty one, and it names the flag that performs the damage as its own remedy, which is the shape this codebase already had to fix twice in `fs_move`. `old_string === new_string` is refused for the same "the operation has no meaning" reason rather than let through as a no-op: fs_edit rewrites through `writeFileAtomic`'s temp-file rename, so identical strings still replace the inode, break any hard link and bump mtime while the bytes stay what they were, and `Replaced N occurrence(s)` is a true sentence that reads as a change that did not happen -- a refusal is the answer that makes an agent look at its own strings, where a `0 changes` success would still be counted as a completed step by anything branching on `isError`. Neither trigger is contrived: both are what an agent produces when a search string came from a variable that resolved empty, or when two template variables resolved to the same value. An empty `new_string` is legitimate (deletion) and is untouched. `old_string` also carries `minLength: 1` in the published schema -- spelled inline rather than by extending `stringProp`, since it is the only length floor in the server -- so a caller that validates before sending sees the constraint without making the call that used to corrupt the file; the handler check is the enforcement, the schema keyword is the courtesy.
- **Byte fidelity is content-based, not extension-based (issue #11).** `fs.readFileSync(path, 'utf-8')` -- the call every one of `fs_read`/`fs_edit`/`fs_grep`'s fallback used -- maps every byte that is not valid UTF-8 to U+FFFD before any of this codebase's own code runs. That mapping is lossy and irreversible the instant it happens: the original byte is gone, and writing the decoded string back (`fs_write`, `fs_edit`) re-encodes each replacement character as three DIFFERENT bytes, silently corrupting the file with no error, warning, or hint anywhere in the path (measured: 4 bytes of latin-1 became 10; 7 bytes of arbitrary binary became 13). The fix is a pass-through principle, not a content judgement: fsMCP does not decide what a file's bytes MEAN -- there is no "this looks like a binary file" heuristic anywhere in this codebase, and in particular no extension-keyed special case (an earlier version of `fs_read` auto-base64'd a fixed set of image extensions; that keyed the decision off a **string**, so two files with byte-identical content and different names behaved differently, and every other non-image binary -- a `.dat`, a latin-1 `.txt`, a UTF-16 file -- still took the lossy path. Removed entirely, not extended, because extending it would mean picking a bigger fixed list instead of fixing the actual question). Instead, every call site that needs to decide asks one question, from the bytes: "can the caller's DECLARED encoding represent these bytes losslessly?" `src/encoding.ts`'s `decodeUtf8Strict()` (`new TextDecoder('utf-8', { fatal: true })`, never `Buffer#toString('utf-8')`, which has no strict mode and is the exact lossy call this issue is about) answers that for UTF-8 text; a hand-rolled byte scanner is deliberately not used in its place, since it would duplicate logic the platform already implements correctly with real ways to get it subtly wrong (an off-by-one on a continuation byte, an overlong encoding accepted). `fs_read` takes an `encoding` argument: `"text"` (default) decodes as UTF-8 and refuses if that fails, naming the file and pointing at `"base64"`; `"base64"` returns the file's exact bytes unconditionally, on any file, decoded or not. `fs_read`'s text mode was already a VIEW before this issue (line-numbered, truncated at 2000 chars per line, `offset`/`limit`-windowed) and is documented as one now rather than implied to be byte-faithful; those view options are meaningless against a byte dump, so `encoding: "base64"` REFUSES `offset`/`limit` rather than silently ignoring them, and returns whole-file bytes with no line numbers and no truncation. **A mode that exists for fidelity must round-trip through itself** (PR #13 review): `fs_read`'s base64 reply (`src/tools/read.ts`) is the BARE base64 payload -- no header, no trailing newline, nothing else in the content string, with the byte count carried structurally in `_meta.bytes` instead -- specifically so `fs_read(base64)` piped straight into `fs_write(base64)`'s `content`, unmodified, is an identity on the file's bytes. An earlier version prefixed a human-readable `"[base64: N bytes]\n"` header; that failed closed rather than corrupting anything (`isValidBase64` refused the header line as malformed base64), but it meant fs_read's own reply was not valid fs_write input, so the obvious composition of the two calls didn't work -- and a caller that "fixed" this by guessing at an unspecified stripping pattern could just as easily strip it wrong and silently corrupt the bytes, reproducing this issue's core failure one level up, looking like a caller bug instead of a design one. Text mode is explicitly exempt from this rule -- it is a documented view (line-numbered, truncated, says so) and never claimed to be an identity. `fs_write` mirrors this: `encoding: "text"` (default, unchanged) writes the UTF-8 encoding of `content` as-is; `encoding: "base64"` decodes `content` as base64 and writes those exact raw bytes (`fs.writeFileSync` with no encoding argument -- passing `'utf-8'` there would re-interpret an arbitrary byte buffer as text, corrupting exactly what this path exists to preserve), after `isValidBase64()` rejects anything outside the base64 alphabet or not block-aligned (Node's own base64 decoder is lenient and silently DROPS invalid characters rather than erroring, which would otherwise let a truncated copy-paste decode to the wrong bytes and still report success). **`fs_write` does NOT refuse U+FFFD in text-mode content** -- a file may legitimately contain the replacement character, and second-guessing the caller's own declared-text content is a content judgement this principle forbids, not a representability question; if a caller writes U+FFFD, that is written, verbatim, like any other character. **A lone (unpaired) UTF-16 surrogate in `content`/`new_string` (possible over JSON-RPC -- `JSON.parse` does not validate surrogate pairing, so a wire string can contain one even though nothing this server itself ever decodes from disk can produce one) IS refused unconditionally, by both `fs_write` and `fs_edit`, with no escape hatch**: this is not a heuristic, because there is no valid UTF-8 encoding for a surrogate code point at all -- Node's encoder would silently substitute U+FFFD for it, the same lossy shape as the rest of this issue, just introduced at the JSON-RPC boundary instead of by a disk read, and refusing has no legitimate case to second-guess since representing it correctly is not possible in the first place. `fs_edit` refuses to operate on a file whose bytes are not valid UTF-8 at all (no base64 mode for it -- a byte-level splice is not a string replacement, and this file does not invent a new operation to paper over that): it is defined over text, and content that is not representable as text has no meaning to find-and-replace against, so refusing is "this operation does not apply," not "binary is dangerous." `fs_grep`'s Node fallback (`grepFallback`) reads with the same `decodeUtf8Strict()` and skips (does not error on) a file that fails it, the same as any other unreadable file -- it only reports, never writes, so there is no write-back to corrupt, but reporting a match against a lossily-substituted line would still hand a caller text that does not match the file with no way to tell; skipping keeps it agreeing with `fs_read` about what it declines to decode. Truncation of an over-long line is flagged twice: the existing inline `"... [truncated]"` marker for a human reader, and `_meta.truncated: true` on the result for a caller that wants to branch on it programmatically instead of pattern-matching English -- a sibling of `_meta.scope_violation` (see below), not a replacement for it; the two never appear on the same result (one is a refusal's `_meta`, the other a success's).
- **fs_move** validates both `source` and `destination` independently and in full (C4), refuses an existing destination unless `overwrite: true`, and refuses moving a directory into (or onto) its own descendant.
- **fs_delete** refuses to remove an `allowed_dir` root itself, defaults `recursive` to `false`, caps a recursive delete at 10,000 entries (refusing past it rather than truncating silently), and relies on `fs.rmSync`'s recursive mode unlinking a symlink it meets rather than following it -- pinned by test, not just assumed.
- **TOCTOU is a documented non-goal (C7),** for every mutating tool including the new ones: winning the check-then-use race requires writing a symlink inside an allowed directory, which the same uid running fsmcp could already do directly. If fsmcp ever runs more privileged than whoever can write into an allowed dir, the fix is `openat`-per-component with `O_NOFOLLOW` from a pinned root fd, not a better check.
- **No throws across tool boundary** -- registry wraps handlers in try/catch as a backstop, but tools are expected to check cleanly (absolute path, NUL bytes, overlong paths -- all centralized in `security.ts`) rather than lean on the catch.

## Adding a Tool

1. Create `src/tools/foo.ts`
2. Export `registerFoo(registry: ToolRegistry)`
3. Define tool with `registry.register({ name, description, inputSchema, category, annotations }, handler)` -- `annotations: { readOnlyHint, openWorldHint }` is required on the type, not optional; set both explicitly and honestly
4. Use `schema()`, `stringProp()`, `intProp()`, `boolProp()`, `enumProp()` from registry. For any path ARGUMENT's description (`file_path`/`path`/`source`/`destination`), use `virtualPathDescription()` (registry.ts) instead of writing your own -- it is the one place that describes the `/<label>/...` address shape without asserting a concrete label (labels are assigned per call, not known when this static schema is built), and every existing tool's path argument goes through it so they stay worded identically. Writing "Absolute path to the file" by hand here is the exact regression a schema-text test (`tests/schema-text.test.js`) exists to catch: that was true before issue #7 and became actively misleading after it.
5. Return via `textResult()` or `errorResult()` from types; use `scopeViolationResult()` (or `checkPath()`/`checkPathNoFollowFinal()` from security.ts, which return it for you) for any refusal that means "outside your scope"
6. Accept `ToolContext` as second arg. For any path ARGUMENT the client supplies, call `decodeInboundPath(arg, ctx.labels)` (vpath.ts) first and use the host path it returns -- not the raw argument -- for everything after. Check that decoded host path with `checkPathV()`/`checkPathNoFollowFinalV()` (vpath.ts) -- not `checkPath()`/`checkPathNoFollowFinal()` (security.ts) directly, or the refusal message will still name the host path, and not `validatePath()` + `errorResult()` by hand, or the refusal won't carry `_meta.scope_violation` when it should. A path the tool itself PRODUCES (a search hit, a directory listing entry) needs `hostToVirtualOrRedact()` (vpath.ts) on the way out. Any OTHER message that embeds a path this handler already decoded (a success sentence, a `file not found`) must be wrapped in `translateResult(result, [thatPath, ...], ctx.labels)` before it is returned -- outbound translation is deliberate per call site, not automatic (see "Outbound translation is deliberate" above); a caught exception's message should go through `describeError(err, ctx.labels)` instead of `err.message` directly, so `err.path`/`err.dest` get translated. Never pass a tool's own file CONTENT (what `fs_read` returns, or a matched line in `fs_grep` content mode) to any of these -- it is not a path, and translating it would corrupt it (PR #10)
7. Import and call `registerFoo(registry)` in `main.ts`
